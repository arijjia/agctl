## 1. Что такое agctl

agctl — платформа агентских рабочих мест. Пользователь работает в браузере
с чат-интерфейсом агента DeepSeek Harness (`dsh`, пакет
`@deepseek-ai/dsh`), а сам агент исполняется в изолированном контейнере,
который agctl создаёт для этого пользователя. Контейнер содержит инструменты
разработчика (git, Node, Python, клиенты GitLab и Jira, MCP-серверы,
браузеры для Playwright в отдельном варианте образа), каталог проектов
`/workspace` и домашний каталог dsh `/home/dsh`, где хранятся сессии,
настройки, плагины и учётные данные агента.

agctl решает задачи, которых у самого dsh нет:

- создаёт, усыпляет и пересоздаёт контейнеры рабочих мест и следит за их
  здоровьем;
- аутентифицирует пользователей и проксирует их браузер к dsh в их
  контейнере, подставляя одноразовый токен загрузки dsh и брендирование
  организации;
- готовит домашний каталог dsh: настройки провайдера модели, плагины
  платформы, пресеты разрешений, скиллы;
- управляет проектами, каталогом «возможностей» (скиллы, шаблоны,
  инструменты профиля) и MCP-серверами для каждого проекта;
- в серверном режиме даёт роли, админ-панель, квоты на токены и SSH для
  разработчиков; в локальном режиме — доступ к папке проектов машины и
  контролируемый мост к командам хоста.

Платформа нейтральна к организации: брендинг, модели по умолчанию, каталог
образов и белый список команд моста задаются **профилем организации** —
каталогом с `profile.yaml` и ассетами (раздел 3.9).

## 2. Три режима и три бинаря

Код состоит из одного ядра (`internal/*`) и трёх точек входа (`cmd/*`),
каждая из которых собирается в отдельный статический Go-бинарь
(`CGO_ENABLED=0`). Ядро содержит HTTP-сервер, адаптеры рантаймов,
подготовку домашнего каталога dsh, хранилище и профиль; точки входа
решают, какие части ядра подключить.

| Бинарь | Исходники | Для кого | Команды | Что в него не входит |
|---|---|---|---|---|
| `agctl` | `cmd/agctl` | разработчик на своей машине | `dev …` (локальный режим), `backlog`, `completion`, `version` | серверные модули, клиенты Kubernetes и AX, gRPC |
| `agctl-server` | `cmd/agctl-server` | организация | `serve`, `migrate`, `seed-demo-users`, `connect`, `sync`, `config`, `completion`, `version` | локальный режим, мост к хосту |
| `agctl-guest` | `cmd/agctl-guest` | образ рабочего места (внутри он лежит как `/usr/local/bin/agctl`); два варианта сборки из одного кода — локальный (только `bridge`, образы `agctl-dsh*`) и серверный (`-tags server`: `ax-runner`, `init-chat-home`, образы `agctl-dsh-server*`) | `bridge` \| `ax-runner`, `init-chat-home` (по варианту), `version` | HTTP-сервер платформы |

Размеры при сборке с `-s -w` (2026-11-16): `agctl` — 19,4 МБ (до
разделения единый бинарь весил 62,4 МБ), `agctl-server` — 61,8 МБ (в нём
клиенты Kubernetes и AX). После разделения guest по режимам (2026-11-18)
под linux с `-s -w`: локальный вариант — 10,8 МБ (без grpc/AX-зависимостей
раннера), серверный — 20,8 МБ.

Из этих бинарей складываются три режима работы:

| | Локальный режим | Серверный режим | Кластерный режим |
|---|---|---|---|
| Запуск | `agctl dev up` | `agctl-server serve` (`--runtime docker`, по умолчанию) | `agctl-server serve --runtime k8s` или `--runtime ax` |
| Пользователи | один владелец машины | много пользователей, роли `user`, `developer`, `admin` | как в серверном |
| Вход | одноразовая ссылка из CLI, без регистрации и пароля | регистрация и пароль (argon2id), cookie-сессия | как в серверном |
| Рабочее место | один контейнер в локальном Docker | контейнер на пользователя в Docker хоста шлюза | под Kubernetes или актор Agent Substrate на пользователя |
| `/workspace` | папка проектов разработчика (bind mount) | `$AGCTL_HOME/chats/u<ID>/work` | подкаталог общего RWX-тома, PVC или том актора |
| Дом данных | `~/.agctl-dev` | `~/.agctl` (`AGCTL_HOME`) | том шлюза `/var/lib/agctl` |
| Адрес UI | `127.0.0.1:8930`, только loopback | `127.0.0.1:8929`; наружу через обратный прокси с TLS | Service `agctl` (порт 80 → 8929); Ingress настраивает оператор |
| Секреты | хранилище ОС (Keychain, Credential Manager, Secret Service) или зашифрованный файл | `.env` хоста и SQLite (AES-256-GCM) | Kubernetes Secret или подстановка ключа на egress-шлюзе Substrate |
| Автосохранение проектов в git | выключено (это настоящие репозитории) | раз в 2 минуты, локальный коммит без push | как в серверном |
| Мост к командам хоста | есть, по белому списку | нет | нет |
| Сон рабочего места | через 12 часов простоя | через 60 минут (пул заранее запущенных рабочих мест реализован, но не подключён к флагам, раздел 10.4) | удаление пода или `SuspendTask` актора |

Технически локальный режим — это тот же сервер `internal/server`, но
запущенный с заполненным `Config.Local` и без серверных модулей; кластерный
режим — тот же серверный режим с другим адаптером рантайма. Поэтому
большинство решений, описанных в разделе 3, действуют во всех режимах.

## 3. Общее ядро

### 3.1 Общая схема запроса

Независимо от режима, путь пользователя к агенту одинаков:

```
браузер ──HTTP(S)──▶ agctl (internal/server)
                      ├─ /api/*            REST API (JSON)
                      ├─ /, /launcher, …   SPA (web/dist, встроена в бинарь)
                      └─ /chat/*  ──────▶ обратный прокси ──▶ dsh web в рабочем месте пользователя
                                            (адрес даёт адаптер рантайма:
                                             Docker — 127.0.0.1:<порт>,
                                             k8s — DNS Service пода,
                                             AX — маршрутизатор Substrate + заголовок актора)
```

dsh web внутри рабочего места слушает порт 3080 на адресе интерфейса
`eth0` контейнера (апстрим dsh запрещает привязку к `0.0.0.0`, поэтому
адрес вычисляет утилита `agctl-dsh-net print` в `entrypoint.sh`). Наружу
этот порт отдаёт механизм рантайма: публикация порта Docker, Service
Kubernetes или маршрутизатор Substrate.

### 3.2 Точки входа и общий `serve`

`internal/cli/serve.go` содержит единственную реализацию команды `serve`.
Её вызывают обе точки входа с разными параметрами `cli.ServeOptions`:

- `agctl-server serve` → `Modules: server.ServerModules()`,
  `Runtime: registerRuntimeFlags` (выбор бэкенда `docker | k8s | ax`,
  `cmd/agctl-server/runtime_select.go`);
- `agctl dev serve` (внутренняя команда, её запускает `agctl dev up`) →
  `Local: &server.LocalMode{…}`, `OnReady` (дополнительный слушатель моста
  и файл состояния), без модулей; бэкенд — только Docker
  (`cli.DockerRuntime`).

`Serve` по порядку: разрешает профиль организации (флаг `--profile`,
`--profile-dir`, переменные окружения, `~/.config/agctl/config.yaml`),
регистрирует флаги (их значения по умолчанию зависят от профиля), собирает
провайдера модели по умолчанию (`provision.Provider`: имя, Base URL, модели,
ключ, дополнительные провайдеры профиля), создаёт дом данных, мастер-ключ
шифрования `secrets.key` и SQLite `agctl.db`, строит сервер через
`Runtime.Build`, запускает фоновые задачи, регистрирует маршруты и слушает
адрес до сигнала завершения. При завершении сервер останавливает живые
рантаймы (тома и домашние каталоги остаются).

Приоритет источников настроек серверного CLI: флаги, затем переменные
окружения `AGCTL_*`, затем `~/.config/agctl/config.yaml`
(`internal/cli/config.go`, путь переопределяет `AGCTL_CONFIG`), затем
встроенные значения. Секреты в `config.yaml` не хранятся — только в
окружении.

### 3.3 HTTP-сервер и подключаемые модули

`internal/server` — один пакет, в котором живёт HTTP-сервер. Метод
`Server.Routes()` регистрирует только то, что нужно во всех режимах:

| Группа маршрутов | Обработчики | Файлы |
|---|---|---|
| Вход и профиль пользователя | `POST /api/login`, `POST /api/logout`, `GET /api/me`, `GET /api/config` | `handlers.go` |
| Проекты | `GET/POST /api/projects`, `DELETE /api/projects/{name}`, инструкции, файлы проекта | `projects.go`, `project_files.go` |
| Каталог и компоненты | `/api/catalog`, `/api/projects/{name}/catalog/…`, `/components`, `/prompt` | `catalog.go`, `project_components.go` |
| MCP-серверы проекта | `GET/PUT /api/projects/{name}/mcp` | `project_mcp.go` |
| Папки чата | `/api/chat/folders`, `/api/chat/sessions/{id}/folder-instructions` | `chat.go` |
| Карта системы | `GET /map`, `GET /map/{name}` | `map.go` |
| Чат | `GET /`, `GET|POST /chat/*` | `chat.go`, `chatshell.go`, `htmlscan.go` |
| Статика SPA | `GET /` (файлы `web/dist`) | `server.go` |

Всё, что нужно только серверу организации, оформлено как **модули**
(`internal/server/modules.go`, тип `server.Module` с полями `Routes` и
`Background`). Модули подключает точка входа через `Config.Modules`;
локальный режим не подключает ни одного, поэтому соответствующих маршрутов
и фоновых задач в нём нет (это проверяет тест
`TestLocalModeHasNoServerModules`).

| Модуль | Что даёт | Файлы |
|---|---|---|
| `registration` | `POST /api/register`: первый аккаунт становится администратором, ограничение частоты регистраций с одного IP (30 в минуту) | `handlers.go`, `internal/auth/ratelimit.go` |
| `roles` | заявки на роль developer (`/api/role-requests`, одобрение администратором), SSH-ключ разработчика (`/api/me/ssh`) | `roles.go` |
| `launcher` | лаунчер разработчика: каталог образов, старт, стоп и логи своего контейнера (`/api/launcher/images`, `/api/me/runtime/*`, `/api/me/image`, `/api/me/containers`), страница `/launcher` | `launcher.go`, `runtime_api.go` |
| `admin` | админ-панель: пользователи, аудит, обзор, контейнеры, журнал запросов шлюза, квоты токенов, траектории агента, лимиты на пользователя (`/api/admin/*`), страница `/admin` | `admin.go`, `admin_sessions.go` |
| `prewarm` | пул заранее запущенных рабочих мест для недавно активных пользователей; работает при `Config.ChatPrewarmN > 0`, но `serve` это поле не выставляет (раздел 10.4) | `chat_prewarm.go` |
| `autosave` | автосохранение проектов в git локальным коммитом без push | `projects.go`, `server.go` |
| `jira` | заготовка опросчика Jira (включается переменными `AGCTL_JIRA_*`) | `jirapoll.go` |
| `ax-provider-config` | `GET /ax/provider-config/{task}`: конфигурация провайдера для раннера AX | `server.go` |

Фоновые задачи ядра (`Server.StartBackground`): усыпление простаивающих
рабочих мест (раз в минуту), сверка состояния рантаймов (раз в 30 секунд:
контейнер, не прошедший `HEALTHCHECK`, забывается и пересоздаётся при
следующем обращении), удаление истёкших сессий (раз в час). Модули
добавляют свои задачи: autosave, prewarm, опросчик Jira.

### 3.4 Аутентификация и авторизация

`internal/auth` реализует хеширование паролей argon2id, выдачу и проверку
cookie-сессий и ограничение попыток входа (10 неудачных попыток —
блокировка логина на 5 минут). Cookie называется `agctl_session`, живёт
7 дней, помечается `HttpOnly` и `SameSite=Lax`; флаг `Secure` ставится при
`--secure-cookies` (когда TLS завершается на доверенном обратном прокси).
Хранилище сессий подключается функциями `SetSession`, `SessionUser`,
`DeleteSession`: в серверном режиме это таблица `sessions` в SQLite, в
локальном — файл сессий владельца (раздел 6.3).

Обработчики оборачиваются в `requireUser`, `requireDeveloper` или
`requireAdmin`; каждый из них получает `identity{ID, Login, Role}`. Запросы,
меняющие состояние, из чужого источника отклоняются проверкой
`sameOriginAuthority` (заголовок `Origin` должен совпадать с `Host`).
Кросс-доменный доступ к `/api` выключен, если не задан точный список
`--cors-origin`.

### 3.5 Менеджер рантаймов и контракт `ChatProvider`

Рабочее место пользователя в коде называется «чат-рантайм». Контракт
адаптера — интерфейс `runtime.ChatProvider` (`internal/runtime/chat.go`):
`EnsureChat(spec)` возвращает дескриптор `ChatHandle` с адресом
(`Endpoint`), дополнительными заголовками (`Headers`), идентификаторами
рантайма и экземпляра; также есть `StopChat`, `LogsChat`, проверка
здоровья и активности SSH. Входные данные — `ChatSpec`: идентификатор
рантайма и хранилища, образ, провайдер модели, рабочий каталог, переменные
окружения разработчика, SSH-ключ, признаки локального режима и
egress-allowlist.

Реализации: `internal/runtime/dockerrt` (Docker Engine API), `k8srt`
(Kubernetes), `axrt` (Google AX поверх Agent Substrate). Выбор делает
`cmd/agctl-server/runtime_select.go`; локальный режим всегда использует
Docker.

`internal/server/chat.go` держит карту «пользователь → живой рантайм».
Функция `ensureChat(userID)`:

1. берёт мьютекс пользователя, чтобы первый старт не выполнялся дважды;
2. если в кэше есть живой рантайм — возвращает его;
3. иначе собирает `ChatSpec`: образ (выбор разработчика из лаунчера или
   образ по умолчанию), провайдера (личный провайдер пользователя из
   таблицы `secrets` или провайдер платформы; при включённых квотах —
   виртуальный ключ LiteLLM), каталог проекта и переменные окружения
   (в локальном режиме — папка разработчика, доступы и адрес моста);
4. записывает файлы доступов агента в домашний каталог dsh
   (`agent_creds.go`);
5. вызывает `chatProvider.EnsureChat` и запоминает результат.

Рабочее место усыпляется после `--chat-ttl-min` минут простоя (60 на
сервере, 720 в локальном режиме). Перед усыплением проверяется, нет ли
активной SSH-сессии разработчика. Тома и домашний каталог при усыплении не
удаляются; следующий запрос к `/chat/` поднимает рантайм заново.

### 3.6 Шлюз чата `/chat/`

`chatProxy` (`internal/server/chat.go`) — обратный прокси `httputil.ReverseProxy`
от браузера к dsh web:

- путь `/chat/x` переписывается в `/x`, заголовки `Host` и `Origin`
  подставляются под адрес рантайма, cookie agctl (`agctl_*`) до рантайма не
  доходят, параметр `token` из адреса удаляется;
- к запросу добавляются заголовки адаптера (для AX — `ate-target-actor`);
- dsh защищает интерфейс одноразовым токеном загрузки. Сервер получает его
  из журнала контейнера (`LogsChat`, последние 80 строк) и подставляет
  `?token=` только при ответе 401 от dsh (`mintTransport` в `gateway.go`);
  в браузер токен не попадает;
- cookie, которые выдаёт dsh (`dsh-auth-*`), ограничиваются путём `/chat/`
  и получают `Secure` при `--secure-cookies`;
- в HTML-ответ до первой отрисовки встраивается «оболочка чата» с брендом
  организации и элементами навигации (`chatshell.go`, `htmlscan.go`);
- если рантайм ещё не поднялся, браузер получает страницу ожидания с
  автоповтором; ошибки соединения помечают рантайм как недоступный, и
  следующий запрос пересоздаёт его;
- запросы чата пишутся в журнал шлюза `proxy_requests` (виден в
  админ-панели).

### 3.7 Подготовка домашнего каталога dsh (`internal/provision`)

Пакет `provision` превращает пустой том в рабочий домашний каталог dsh и
поддерживает его в актуальном состоянии:

- `SeedDshHome` — первое заполнение из скелета `internal/assets/dsh-skel`
  (встроен в бинарь);
- `RefreshProvider` — при каждом старте переписывает `settings.yaml`
  (провайдеры модели: имя, Base URL, модели, имя переменной ключа
  `apiKeyEnv`), патч `profiles/web/cordis.patch.yml` и файл
  `.credentials.yaml` (права 0600) со значениями ключей. dsh берёт ключ из
  этого файла; в переменных окружения контейнера ключей модели нет
  (раздел 8.4);
- `EnsureChatPlugins` / `EnsureChatPluginsLocal` — устанавливают плагины
  платформы из `dsh-plugins/` (брендирование `chat-brand`, панель
  «Кабинет» `cabinet` только на сервере, папки сессий
  `chat-session-files`, консоль «Возможности» `workspace-console`);
- `EnsurePermissionDefaults` — пресет разрешений агента по умолчанию;
- `projects.go`, `catalog.go`, `components.go` — проекты как нативные
  рабочие пространства dsh, каталог возможностей профиля, включение и
  выключение компонентов;
- `mcp_preset.go` — каталог MCP-серверов платформы (DuckDuckGo, Context7,
  GitLab, Jira через `uvx mcp-atlassian`, Playwright, «Мост к хосту» только
  в локальном режиме) и генерация пресета MCP для каждого проекта с
  пробросом нужных переменных окружения;
- `local_workroot.go` — в локальном режиме рабочий корень владельца
  указывает на его папку проектов;
- `provision.go`, `kits.go` — провижининг рабочих мест версии до 3
  (bare-репозиторий и клон); оставлен для старых записей.

### 3.8 Хранилище и шифрование

`internal/store` — SQLite через `modernc.org/sqlite` (чистый Go, без cgo),
режим WAL, `busy_timeout` 5 секунд, внешние ключи включены. Схема
применяется миграциями из `internal/store/migrations` (встроены в бинарь)
при открытии базы; команда `agctl-server migrate` делает то же явно.
Подробности схемы — раздел 8.1.

`internal/secrets` шифрует значения AES-256-GCM мастер-ключом из 32
случайных байт в `$AGCTL_HOME/secrets.key` (права 0600). Так хранятся
провайдер модели платформы, личные провайдеры пользователей, токен раннера
AX и другие чувствительные настройки.

### 3.9 Профиль организации (`internal/profile`)

Профиль — данные, а не код: `profile.yaml` (секции `brand`, `login`, `llm`,
`help`, `map`, `examples`, `images`, каталог возможностей) и ассеты
(логотипы, Dockerfile надстройки образа, каталог `local/` для локального
режима). Встроенный нейтральный профиль `agctl` лежит в
`internal/profile/profiles/agctl`; профили организаций живут в отдельных
приватных репозиториях `agctl-profile-<id>` и подключаются каталогом
(`--profile-dir`) или по имени из `./profiles` и `$AGCTL_HOME/profiles`
(`make profile-fetch`). Профиль задаёт:

- брендинг: передаётся в браузер единственным каналом — объектом
  `window.__AGCTL_BRAND__`, который сервер встраивает в `<head>`;
- провайдера модели по умолчанию и дополнительных провайдеров (ключи — только
  через переменные окружения, имена которых указаны в профиле);
- каталог образов лаунчера `images.dev` и надстройку образа
  `images.dockerfile` с вариантами `image/flavors/*`;
- белый список команд моста для локального режима
  (`local/bridge-tools.yaml`).

Тест `TestCoreIsOrganizationFree` проверяет, что в ядре нет строк,
относящихся к конкретным организациям.

### 3.10 Веб-интерфейс и плагины dsh

`web/` — одностраничное приложение на React (Vite). Сборка `make web_build`
кладёт результат в `web/dist`, который хранится в репозитории и встраивается
в бинарь через `go:embed`. Компоненты: страница входа и регистрации
(`App.tsx`), лаунчер разработчика (`Launcher.tsx`, сервер), лаунчер
локального режима (`LocalLauncher.tsx`; `App.tsx` выбирает его, если
`GET /api/local/ui` отвечает 200), админ-панель (`AdminPanel.tsx`,
`charts.tsx`), просмотр логов (`LogsPanel.tsx`). Основная работа
пользователя идёт не в SPA, а в интерфейсе dsh под `/chat/`.

`dsh-plugins/` — плагины, расширяющие интерфейс dsh: `chat-brand`
(брендирование и навигация), `cabinet` (панель «Кабинет» на сервере:
SSH-ключ, роль, проекты), `chat-session-files` (папки проектов слева,
файлы сессий), `workspace-console` («Возможности»: каталог, компоненты,
MCP проекта). Их копии лежат в `internal/assets/dsh-skel`; хук pre-commit
проверяет, что копии совпадают.

## 4. Серверный режим на одном Docker-хосте

### 4.1 Процессы и соединения

```
Пользователи (браузеры)                     Разработчик (терминал)
        │ HTTPS                                    │ SSH через туннель/VPN до хоста
        ▼                                          │
Обратный прокси организации (TLS)                 │
        │ HTTP                                     │
        ▼                                          ▼
┌─────────────────────────── хост шлюза ───────────────────────────────────┐
│ agctl-server serve           127.0.0.1:8929 (--addr)                      │
│   ├─ REST API, SPA, шлюз /chat/, модули, фоновые задачи                   │
│   ├─ $AGCTL_HOME: agctl.db (SQLite WAL), secrets.key, chats/u<ID>/…       │
│   └─ Docker Engine API (unix-сокет /var/run/docker.sock)                  │
│                                                                           │
│ dockerd                                                                   │
│   └─ контейнер agctl-chat-<хеш дома>-u<ID>  (по одному на пользователя)   │
│        ├─ dsh web  eth0:3080  ── публикация ──▶ 127.0.0.1:<свободный порт>│
│        ├─ sshd     :2222 (только developer)  ──▶ 127.0.0.1:<порт SSH>     │
│        ├─ /workspace ◀── bind ── $AGCTL_HOME/chats/u<ID>/work             │
│        └─ /home/dsh  ◀── bind ── $AGCTL_HOME/chats/u<ID>/dsh-home         │
└───────────────────────────────────────────────────────────────────────────┘
        │ HTTPS 443 (DNS провайдера закреплён в /etc/hosts контейнера)
        ▼
Провайдер модели (LiteLLM организации или публичный), GitLab, Jira
```

На хосте постоянно работают два процесса: `agctl-server serve` и `dockerd`.
Контейнер рабочего места появляется при первом обращении пользователя к
`/chat/` и останавливается после часа простоя. SQLite и git — библиотеки внутри
процесса сервера, а не отдельные процессы.

### 4.2 Сеть контейнера рабочего места

`dockerrt.Start` (`internal/runtime/dockerrt/docker.go`) создаёт контейнер
со следующими сетевыми свойствами:

- порт 3080 публикуется только на `127.0.0.1` хоста, на свободный порт,
  который сервер выбирает сам (`net.Listen("tcp", "127.0.0.1:0")`). Снаружи
  хоста dsh недоступен; доступ к нему возможен только через шлюз `/chat/`;
- порт 2222 (sshd) публикуется на `127.0.0.1` только для роли developer и
  только если пользователь сохранил публичный ключ, а образ не помечен как
  вариант без SSH (`agctl-dsh-nossh`, `AGCTL_NO_SSHD=1`). sshd принимает
  только ключи, вход по паролю и перенаправления портов выключены;
- `host.docker.internal` указывает на хост (`host-gateway`): так рабочее
  место может обратиться к сервисам на хосте;
- для каждого хоста провайдера модели сервер заранее разрешает DNS на хосте
  и добавляет запись в `/etc/hosts` контейнера (`pinsForBaseURLs`). Это
  нужно, когда провайдер доступен только через корпоративный DNS или VPN
  хоста;
- лимиты памяти и CPU — флаги `--mem-gb` и `--cpus` (по умолчанию 2 ГБ и
  2 ядра); политика перезапуска — `no` (сервер сам решает, когда
  пересоздавать);
- на контейнер ставятся метки рабочего места, версии сборки agctl и
  желаемого образа. При старте сервер удаляет контейнеры прошлой сборки
  (`SweepVersionDrift`), а при каждом старте рабочего места пересоздаёт
  контейнер, собранный не из желаемого образа (данные на томах сохраняются).

**Egress-allowlist** (`internal/runtime/dockerrt/egress.go`, поле
`Config.EgressAllowlist`; флага в `serve` сейчас нет, поэтому механизм
реализован и покрыт тестом, но из CLI не включается — раздел 10.4).
Контейнеры переводятся в
выделенную сеть `agctl-egress-<хеш дома>`, а в цепочку `DOCKER-USER`
вставляется собственная цепочка правил: из подсети разрешены ответы по уже
установленным соединениям, DNS (UDP и TCP 53) и трафик к шлюзу сети (то есть
к хосту и сервисам на нём); всё остальное отбрасывается. Правила применяет
вспомогательный контейнер того же образа с `--network host` и
`NET_ADMIN`, поэтому механизм работает и на Linux, и в Docker Desktop
(где `DOCKER-USER` находится во внутренней виртуальной машине).

### 4.3 Пользователи, роли и доступ разработчика

Первый зарегистрированный аккаунт становится администратором, остальные —
пользователями. Пользователь может подать заявку на роль developer;
администратор одобряет её в админ-панели (миграция `011_role_requests`).
Роли различаются так:

- **user** — чат с агентом в личном рабочем месте;
- **developer** — то же плюс лаунчер (выбор образа из каталога, старт,
  стоп, логи своего контейнера), SSH в свой контейнер и проброс доменных
  переменных хоста `--dev-env` (например, токенов GitLab и Jira из `.env`);
- **admin** — всё перечисленное плюс админ-панель.

SSH разработчика: ключ сохраняется через `PUT /api/me/ssh`, порт 2222
контейнера публикуется на loopback хоста, поэтому подключение снаружи
возможно только через SSH-туннель или VPN к хосту шлюза. Команды
`agctl-server connect` (собирает и запускает `ssh` с проверкой хоста и
порта) и `agctl-server sync` (синхронизация папки с `/workspace` через
Mutagen) помогают это сделать.

### 4.4 Проекты, автосохранение и админ-панель

Проекты пользователя — подкаталоги `/workspace`, зарегистрированные в dsh
как рабочие пространства. Модуль `autosave` раз в 2 минуты делает
локальный git-коммит изменений в каждом проекте (без push; удалённый
репозиторий у проекта не создаётся). Подключение внешнего git — отдельная
задача (карточка `git-remote-push-optin`).

Админ-панель показывает пользователей и их роли, аудит действий, сводку
(активные рантаймы, попадания в пул prewarm, холодные старты), контейнеры
с действиями stop, start, restart и логами, журнал запросов шлюза, квоты
токенов и траектории агента (сервер читает сессии dsh из томов
пользователей). При включённых квотах (`Config.LiteLLMQuotas` с адресом и
ключом admin-API LiteLLM, `litellm.go`; флагов в `serve` для них сейчас нет,
раздел 10.4) сервер выпускает каждому пользователю виртуальный ключ
LiteLLM через его admin-API и подставляет этот ключ провайдеру рабочего
места вместо общего; при смене квоты ключ перевыпускается.

### 4.5 Как запустить на одной машине

Из исходников: `make up PROFILE=<id>` собирает SPA, бинари и образ и
поднимает `agctl-server serve` в фоне на `127.0.0.1:8929` с домом
`~/.agctl`; `make corp` — то же с корпоративным LiteLLM (ключ в `.env`);
`make demo` — изолированный демонстрационный стенд в `/tmp` на порту 8930
(конфликтует с локальным режимом); `make stop`, `make down`,
`make logs`, `make status` управляют этими экземплярами. В
производственной установке перед сервером ставится обратный прокси с TLS,
сервер запускается с `--secure-cookies`, а ключ модели передаётся
переменной окружения `AGCTL_LLM_API_KEY` (после первого запуска он хранится
зашифрованным в SQLite).

## 5. Кластерный режим: Kubernetes и Google AX

### 5.1 Общее

В кластере используется тот же бинарь `agctl-server` в образе
`agctl-serve` (`deploy/serve.Dockerfile`: distroless, пользователь 1000,
команда `serve --addr 0.0.0.0:8929`). Бэкенд выбирается флагом
`--runtime` или переменной `AGCTL_RUNTIME`. Оба кластерных адаптера
реализуют `ChatProvider`; старые рабочие места версии до 3 в кластере не
поддерживаются. Лимиты CPU и памяти рабочего места задают те же
`--cpus` и `--mem-gb`.

### 5.2 Развёртывание шлюза (`deploy/k8s`)

Базовые манифесты (kustomize, пространство имён `agctl`):

| Объект | Назначение |
|---|---|
| Deployment `agctl` | 1 реплика, стратегия `Recreate`; порт 8929; пробы `GET /`; файловая система контейнера только для чтения; переменные `AGCTL_HOME=/var/lib/agctl`, `AGCTL_RUNTIME=k8s`, `AGCTL_K8S_*`, `AGCTL_PROFILE_DIR=/etc/agctl/profile`; ключи модели — из Secret `agctl-llm` |
| PVC `agctl-home` (RWO, 5 ГБ) | дом шлюза: SQLite, мастер-ключ |
| PVC `agctl-data` (RWX, 100 ГБ) | общий том данных пользователей, смонтирован в шлюз как `/var/lib/agctl/chats` |
| ConfigMap `agctl-profile`, `agctl-profile-assets` | профиль организации (`make k8s_profile`) |
| Service `agctl` | ClusterIP, порт 80 → 8929 |
| NetworkPolicy `agctl-gateway` | вход к 8929 только из пространства имён `ingress-nginx` и из подов своего пространства имён |
| ServiceAccount `agctl` + Role `agctl-runtime` | права на поды, сервисы, PVC, секреты, network policies, `pods/log` (чтение), `pods/exec` (создание) |

Ingress в репозитории не описан: оператор кластера добавляет его сам вместе
с TLS. Overlay `kind` нужен для локального смоук-теста (NodePort 30929,
образы без реестра, отдельный PVC на пользователя), overlay `ax` — для
бэкенда AX (раздел 5.4).

### 5.3 Бэкенд Kubernetes (`internal/runtime/k8srt`)

На каждого пользователя адаптер создаёт:

| Объект | Имя | Свойства |
|---|---|---|
| Pod | `agctl-chat-<16 hex>` | init-контейнер `seed-dsh-home` и контейнер `dsh`; `runAsNonRoot` (uid 1000), seccomp `RuntimeDefault`, все capabilities сброшены; токен ServiceAccount не монтируется; при заданном `--k8s-runtime-class` — свой RuntimeClass (например gVisor) |
| Хранилище | подкаталог `<StorageID>/` общего тома `agctl-data` либо PVC `data-agctl-storage-<16 hex>` (RWO, `--k8s-storage-size`, по умолчанию 5 ГБ) | `/workspace` ← `work`, `/home/dsh` ← `dsh-home` |
| Secret | `llm-agctl-storage-<16 hex>` | значения ключей модели; в спецификацию пода ключ попадает ссылкой `secretKeyRef`, а не строкой |
| Service | `chat-agctl-chat-<…>` | ClusterIP, порт 80 → 3080 |
| Service SSH | `ssh-agctl-chat-<…>` | NodePort → 2222; создаётся только при ключе разработчика и заданном `--k8s-ssh-host` |
| NetworkPolicy | `net-agctl-chat-<…>` | вход к 3080 только от подов шлюза (селектор `--k8s-gateway-selector`); при SSH — вход к 2222 без ограничения источника; исходящий трафик по умолчанию не ограничивается — см. opt-in egress-политику ниже |

Init-контейнер выполняет `agctl init-chat-home` (серверный вариант бинаря
`agctl-guest` в образе `agctl-dsh-server`): заполняет пустой домашний
каталог скелетом, при необходимости
обновляет провайдера, ставит плагины и пресет разрешений. Готовность пода
проверяется TCP-пробой порта 3080; проба живости (флаг `--k8s-liveness`,
по умолчанию включена) выполняет `agctl-dsh-net health`. Сервер ждёт
состояния Ready до `--k8s-ready-timeout` (180 секунд).

Шлюз обращается к рабочему месту по адресу
`http://chat-<под>.<namespace>.svc.cluster.local:80`, токен загрузки dsh
читает через `pods/log`, активность SSH проверяет через `pods/exec`.
Усыпление удаляет под, сервисы и NetworkPolicy, но сохраняет данные и
Secret. Под с другим образом или версией сборки пересоздаётся.

С включённым SSH под запускается от root с дополнительными capabilities,
необходимыми sshd (CHOWN, DAC_OVERRIDE, FOWNER, SETGID, SETUID,
SYS_CHROOT, KILL, AUDIT_WRITE); это осознанная уступка, о которой стоит
помнить при выборе Pod Security.

#### Opt-in egress-политика чат-подов (карточка k8s-pod-egress-policy)

`--k8s-egress-policy` (env `AGCTL_K8S_EGRESS_POLICY`, config
`serve.k8s.egress_policy`, off по умолчанию) — отдельная политика
`netegress-<…>` на чат-под: DNS (udp/tcp 53) к kube-dns + ipBlock /32
CIDR'ы resolved-хостов провайдеров (`AllProviderURLs`: базовый + Extras).
Шлюз ресолвит при старте чата и обновляет политики живых чатов каждые
10 минут (динамические IP LLM-хостов), при StopChat политика удаляется.
Полный провал ресолва — громкий отказ EnsureChat (чат без хода к LLM
неработоспособен). Ограничение v1: ipBlock видит только IP, порты
LLM-хостов не фильтруются; L7/FQDN (Cilium NetworkPolicy) — отдельная
волна при потребности эксплуатации. Требует CNI с поддержкой
NetworkPolicy (kindnet в kind не энфорсит; смоук `EGRESS=1
make k8s_e2e_kind` ставит Calico и проверяет блокировки).

#### HA control plane (карточка ha-control-plane)

При 2+ репликах шлюза: `--ha-leader-lease=agctl-leader` (env
`AGCTL_HA_LEADER_LEASE`, config `serve.ha_leader_lease`) — фоновые циклы
(рипер TTL, prewarm, autosave, reconcile, jira, чистка сессий, свип
дрейфа) выполняет только реплика-лидер через coordination.k8s.io Lease
(`internal/leaderelection`, LeaseDuration 15 c / renew 5 c, фолловер
берёт лидерство после истечения). Фолбэк single-реплики — флаг не задан,
циклы в процессе как раньше. Хранилище: `--store-dsn` — файл SQLite
(дефолт `$AGCTL_HOME/agctl.db`) или DSN `postgres://…` (PG-бэкенд для
2+ реплик; `internal/store`, диалектный слой + crosstest-матрица).
Overlay двух реплик с PDB — `deploy/k8s/overlays/ha`; kill-под-смоук —
`bin/e2e-ha-kind.sh`.

#### Смоук kind

`make k8s_e2e_kind` (docker, kind, kubectl): образ через `kind load`,
overlay `deploy/k8s/overlays/kind` (PVC на пользователя, NodePort 30929),
регистрация admin+user, `/chat/` от user → под dsh поднят и отдаёт
чат-шелл → `POST /api/me/runtime/stop` → под удалён, PVC цел. Если
NodePort с хостом не доносится (Docker Desktop, colima, nested docker) —
скрипт сам падает на `kubectl port-forward` (BASE_URL задаёт адрес
явно). Пилот ax на kind — `deploy/k8s/overlays/ax-kind`, порт-forward на
service port 80; mTLS-роутер Substrate — `ChatHandle.TLSConfig`.

### 5.4 Бэкенд Google AX и Agent Substrate (`internal/runtime/axrt`)

Каждому пользователю соответствует задача (Task) AX `agctl-<id рантайма>`
в atespace `--ax-atespace` (по умолчанию `agctl`). Сервер управляет ею по
gRPC через `ax-server` (`--ax-server`, по умолчанию
`ax-server.ax-system.svc.cluster.local:8080`, без TLS): создаёт, при
необходимости возобновляет (`ResumeTask`) и ждёт готовности до
`--ax-ready-timeout`. Усыпление — `SuspendTask`: актор сохраняется вместе
со своим томом `/workspace`, который является единственным хранилищем
пользователя (общий RWX-том в overlay `ax` не используется). Образ
обязан быть закреплён по digest (`…@sha256:…`).

Внутри песочницы PID 1 — раннер `agctl ax-runner` (серверный вариант
бинаря `agctl-guest`): он готовит домашний каталог dsh, запускает и перезапускает `dsh web`,
слушает порт 80 (HTTP/1.1 и h2c) и проксирует запросы на dsh
`<eth0>:3080`. Служебные адреса раннера: `/healthz`, `/readyz` (проверка
соединения с dsh) и `/agctl/boot-log` (буфер журнала запуска, только с
токеном раннера) — из него шлюз получает токен загрузки dsh.

Трафик чата идёт на маршрутизатор Substrate (`--ax-router-url`, по
умолчанию `http://atenet-router.ate-system.svc.cluster.local:80`) с
заголовком `ate-target-actor: <atespace>/<task>`, который выбирает
актора.

Конфигурацию провайдера модели раннер получает при каждой загрузке у шлюза:
`GET <PublicURL>/ax/provider-config/<task>` с токеном раннера (32 случайных
байта, создаются один раз и хранятся зашифрованными в SQLite). Поэтому
смена провайдера не меняет спецификацию задачи и не требует её
пересоздания. Адрес шлюза для песочниц — `--public-url`, иначе
`http://<исходящий IPv4 хоста>:<порт>`.

Ключ модели (`--ax-inject-llm-key`): по умолчанию ключ передаётся в
песочницу (в конфигурации провайдера). При значении 0 и заданном
`--ax-ate-api` шлюз сам создаёт Secret `agctl-llm-<хеш>` и политику
исходящего трафика актора: egress-шлюз Substrate подставляет настоящий
ключ в заголовок `Authorization`, а песочница получает только заглушку.
Это единственный режим, в котором агент не может прочитать ключ модели.

Флаг `--ax-debug-ssh` включает отладочные gRPC-сервисы Substrate (процессы
и файловая система) на том же порту 80 раннера; это даёт произвольное
исполнение команд в песочнице и включается только сознательно.

## 6. Локальный режим

### 6.1 Процессы, порты, файлы

```
Машина разработчика
│
├─ agctl dev <команда>             кратковременный CLI (init, up, status, secrets, bridge …)
│      │  читает ~/.agctl-dev/dev.yaml и run/state.json
│      │  управляет фоновым процессом по HTTP с токеном управления
│      ▼
├─ agctl dev serve  (фоновый Go-процесс, 127.0.0.1:8930)
│      ├─ internal/server с Config.Local: владелец без учётной записи, /local/login, /launcher
│      ├─ ~/.agctl-dev/data: agctl.db (settings, аудит), local-sessions.json, chats/u1/dsh-home
│      ├─ мост к хосту: белый список argv, подтверждения, журнал logs/bridge.log
│      ├─ Linux: второй слушатель на IP docker0, только пути моста
│      └─ Docker Engine API (тот же internal/runtime/dockerrt, что на сервере)
│             │
│             ▼
├─ контейнер рабочего места (agctl-dsh[-web|-<профиль>[-<вкус>]])
│      ├─ dsh web на eth0:3080, опубликован на 127.0.0.1:<свободный порт>
│      ├─ /workspace  ◀── bind ── папка проектов (dev.yaml: workdir или аргумент up)
│      ├─ /home/dsh   ◀── bind ── ~/.agctl-dev/data/chats/u1/dsh-home
│      ├─ agctl bridge … ──HTTP + токен моста──▶ http://host.docker.internal:8930/api/local/bridge/*
│      └─ ──HTTPS──▶ модель (LiteLLM организации или публичный провайдер), GitLab, Jira
│
└─ Docker Desktop / Docker Engine / Colima
```

Постоянно работают два процесса: фоновый `agctl dev serve` и Docker.
После нажатия «Запустить» в лаунчере (или сразу после входа, если образ
есть на машине и ключ модели задан) добавляется контейнер с dsh web.
Мост к хосту не держит процессов: вызов агента превращается в однократный
запуск одной команды из белого списка.

Дом режима `~/.agctl-dev` (переопределяет `AGCTL_DEV_HOME`,
`internal/localmode.Home`):

| Путь | Содержимое | Кто пишет |
|---|---|---|
| `dev.yaml` | профиль или `profile_dir`, `image`, `flavor`, `workdir`, `addr`, `mem_gb`, `cpus`, несекретные `env` (адреса, логины), **имена** секретов, `bridge.tools`, `previous_image` | `dev init`, `dev secrets`, лаунчер, `dev update` |
| `data/` | дом сервера: `agctl.db` (SQLite WAL), `secrets.key`, `local-sessions.json` (0600), `chats/u1/dsh-home` (сессии и настройки dsh) | `agctl dev serve` |
| `run/state.json` (0600) | PID, адрес, токен управления, токен входа, образ, папка, время старта, версия и сборка | `dev serve` при готовности; удаляется при выходе |
| `logs/serve.log` | вывод фонового процесса | `dev up` открывает, `dev serve` пишет |
| `logs/bridge.log` | журнал вызовов моста (JSON lines, без вывода команд) | `internal/localbridge` |
| `backups/` | три последних tar-архива домашнего каталога dsh, создаются перед `update` | `localmode.Backup` |
| `secrets.enc` и ключ | запасное зашифрованное хранилище секретов | `localmode.Store` |
| `serve-config.yaml` | пустая заглушка: на неё указывает `AGCTL_CONFIG`, чтобы серверный `~/.config/agctl/config.yaml` не влиял на локальный режим | — |

Перед стартом `devServe` удаляет из окружения процесса `AGCTL_PROFILE`,
`AGCTL_PROFILE_DIR`, `AGCTL_ADDR`, `AGCTL_DEV_ENV`, `AGCTL_DEV_IMAGES`,
`AGCTL_HOME`, поэтому серверные настройки машины на локальный режим не
влияют.

### 6.2 Три токена

`devServe` генерирует три случайных токена (`localmode.NewToken`) и
передаёт их серверу в `server.LocalMode`:

| Токен | Кто знает | Где проверяется | Назначение |
|---|---|---|---|
| токен входа | `run/state.json` → `dev up` / `dev open` → браузер | `GET /local/login?token=` | вход владельца без пароля; действует до перезапуска процесса |
| токен управления | `run/state.json` → CLI на хосте | `GET /api/local/status`, `POST /api/local/shutdown`, `GET /api/local/bridge/pending`, `POST /api/local/bridge/pending/{id}/{approve|deny}` | команды `dev status`, `down`, `bridge pending`, `approve`, `deny` |
| токен моста | переменная `AGCTL_BRIDGE_TOKEN` контейнера и файл `/home/dsh/.agctl/bridge.json` | `GET /api/local/bridge/tools`, `POST /api/local/bridge/call` | вызовы моста из контейнера |

Токены сравниваются за постоянное время (`subtle.ConstantTimeCompare`).
Файл состояния доступен только пользователю машины. Обработчики лаунчера
(`/api/local/ui*`) работают по cookie-сессии владельца и отклоняют
изменяющие запросы из чужого источника (`requireLocalOwner`).

### 6.3 Жизненный цикл: от `init` до чата

**`agctl dev init`** (`devInit` в `cmd/agctl/dev.go`):

1. профиль: `--profile ID` (встроенный `agctl`, `profiles/<id>` из
   исходников, `~/.agctl-dev/profiles/<id>`, `~/.agctl/profiles/<id>` или
   каталог данных пользователя, куда установщик кладёт профиль комплекта;
   если там ровно один профиль организации, он предлагается по умолчанию)
   или `--profile-dir DIR` (сохраняется абсолютным путём);
2. белый список моста: если в `dev.yaml` его нет, берётся
   `local/bridge-tools.yaml` профиля;
3. образ: `--image`, иначе `--flavor` (первый образ профиля с этим вкусом в
   имени), иначе первый из `images.dev` профиля, иначе `agctl-dsh:0.2.2`;
4. папка проектов: `--workdir` или вопрос; весь `$HOME` и корень `/`
   запрещены (`localmode.ValidateWorkDir`);
5. с `--cli` — мастер в терминале (образ, доступы, `docker pull`); без
   него образ и доступы настраиваются в лаунчере.

**`agctl dev up [DIR]`** (`devUp`):

1. читает `dev.yaml` и проверяет папку. Если фоновый процесс уже работает,
   но собран другой версией бинаря (поле `build` в `run/state.json`), он
   перезапускается, чтобы применились исправления новой версии; процесс
   той же сборки с той же папкой просто получает новое окно браузера;
2. проверяет Docker (`dockerrt.PingDaemon`) и свободен ли адрес;
3. запускает себя как `agctl dev serve --workdir DIR` в фоне с выводом в
   `logs/serve.log`, отвязанным от терминала (`Setsid` на Unix,
   `DETACHED_PROCESS` на Windows); `--foreground` оставляет процесс в
   текущем терминале;
4. ждёт `run/state.json` и ответа `/api/local/status` до 3 минут;
5. открывает `http://127.0.0.1:8930/local/login?token=…` в браузере.

**`agctl dev serve`** (`devServe`, внутренняя команда):

1. читает `dev.yaml`, открывает хранилище секретов, собирает окружение
   контейнера (`localmode.ContainerEnv`), кладёт ключ модели в окружение
   процесса как `AGCTL_LLM_API_KEY` (его получает сервер как провайдера;
   в контейнер ключ попадает только файлом, раздел 8.4);
2. собирает `server.LocalMode` (имя владельца, папка, три токена, адрес
   моста `http://host.docker.internal:<порт>`, белый список, журнал,
   окружение, обработчики лаунчера `devHooks`);
3. вызывает общий `cli.Serve` с флагами `--home ~/.agctl-dev/data`,
   `--addr`, `--mem-gb`, `--cpus`, `--chat-ttl-min 720`, `--dev-env=`
   (пусто: окружение хоста не пробрасывается) и профилем;
4. в `OnReady` на Linux поднимает слушатель моста на IP `docker0`, пишет
   `run/state.json` и удаляет его при завершении.

**Инициализация сервера** (`initLocal` в `internal/server/local.go`):

- владелец — не учётная запись (`local_owner.go`): строки в `users` и
  пароля нет, роль developer задана конфигурацией (`roleOf`); ID равен 1,
  а на установке, созданной до этой модели, — ID прежней строки `owner`
  (так сохраняется путь `chats/u<ID>` и сессии dsh);
- сессии браузера хранятся в `data/local-sessions.json` (0600): sha256
  токенов и сроки действия; файл переживает перезапуск процесса;
- создаётся мост (`localbridge.New`), рабочий корень владельца
  переключается на его папку, текущий образ из `dev.yaml` записывается в
  настройку лаунчера.

**Вход** (`handleLocalLogin`): проверка токена входа, выдача cookie-сессии,
переход на `/launcher`. Если ключ модели задан и выбранный образ есть на
машине, рабочее место запускается сразу.

**Лаунчер** (`web/src/LocalLauncher.tsx`):

- «Рабочее место»: каталог образов профиля с отметкой «есть на машине»,
  папка проектов, кнопки «Запустить» и «Перезапустить», ход подготовки
  образа (последние 40 строк журнала);
- «Доступы»: ключ модели, GitLab, Jira, свои переменные. Значения
  никогда не возвращаются в браузер, только признак «задан» и место
  хранения. Смена ключа модели применяется без перезапуска сервера; смена
  остальных доступов или образа при работающем месте предлагает
  перезапуск.

**Старт рабочего места** (`startLocalRuntime` в `local_ui.go`): в фоне
останавливает старое рабочее место при перезапуске, готовит образ, если
его нет (`docker pull`, иначе сборка цепочки образов), затем вызывает
общий `ensureChat`. Отличия от сервера — только в `localChatExtras`:
`/workspace` указывает на папку разработчика, в окружение добавляются
доступы и адрес моста; после старта в домашний каталог dsh кладётся скилл
`agctl-host-bridge`.

**Чат**: браузер → `/chat/` → тот же `chatProxy`, что на сервере →
`127.0.0.1:<порт>` → dsh web.

**`agctl dev down`**: `POST /api/local/shutdown` с токеном управления →
корректное завершение сервера → остановка контейнера; данные остаются.

### 6.4 Обновление и откат

`agctl dev update [--image REF]` выполняет пять шагов с автоматическим
откатом:

1. определяет текущий образ и целевой (флаг или тот же тег заново);
2. `docker pull`; если реестр образ не отдал, но он есть локально, берётся
   локальный; если ID образа не изменился — «уже актуально»;
3. останавливает платформу, делает резервную копию домашнего каталога dsh
   (`backups/dsh-home-<время>-before-<образ>.tar.gz`, хранятся три
   последних) и записывает в `dev.yaml` `previous_image` и `image`;
4. поднимает платформу с той же папкой;
5. проверяет, что рабочее место перешло в состояние `running` (до 5 минут).

Сбой на шагах 4 или 5 вызывает откат: остановку, восстановление домашнего
каталога из резервной копии и возврат прежнего образа.
`agctl dev rollback [--restore-data]` меняет образы местами и при флаге
восстанавливает данные dsh. «Управляемые слои» домашнего каталога
(бренд, плагины, провайдер, пресеты) при старте на новом образе
перезаписываются из скелета; пользовательские настройки и сессии не
затрагиваются.

### 6.5 Доступы и секреты разработчика

Секреты хранит `internal/localmode/secrets.go` через
`github.com/zalando/go-keyring` (сервис `agctl-dev`): Keychain на macOS,
Диспетчер учётных данных на Windows, Secret Service на Linux. При открытии
выполняется пробная запись; если хранилища ОС нет (Linux без
gnome-keyring, WSL, CI) или задано `AGCTL_DEV_SECRETS=file`, используется
файл `secrets.enc`, зашифрованный AES-GCM. Несекретные значения
(`GITLAB_URL`, `JIRA_URL`, `JIRA_USER` и любые с `--plain`) хранятся в
`dev.yaml`.

Контейнер получает все `env` из `dev.yaml` и все секреты, кроме ключа
модели, плюс производные имена для штатных инструментов:

| Исходная переменная | Производные |
|---|---|
| `GITLAB_URL` | `GITLAB_HOST` (glab), `GITLAB_API_URL` = `<url>/api/v4` (MCP GitLab) |
| `GITLAB_TOKEN` | `GITLAB_PERSONAL_ACCESS_TOKEN` (MCP GitLab) |
| `JIRA_API_TOKEN` | `JIRA_PERSONAL_TOKEN` (mcp-atlassian) |
| `JIRA_USER` | `JIRA_USERNAME` |

Инструмент bash в dsh запускает команды агента с очищенным окружением:
переменные с `KEY`, `TOKEN`, `SECRET`, `PASSWORD` в имени до команд не
доходят. Поэтому `internal/server/agent_creds.go` дополнительно кладёт
доступы файлами в `/home/dsh/.agctl` (каталог 0700, файлы 0600):
`credentials.env` (о нём агенту сообщает скилл `agctl-workspace-access`,
не раскрывая значений), `git-credentials` и `gitconfig` (git push в GitLab
по токену через `GIT_CONFIG_GLOBAL`), `glab/config.yml`, `bridge.json`.
Пустой набор доступов удаляет каталог. Этот механизм работает и на сервере
для переменных `--dev-env` разработчика.

### 6.6 Мост к хосту

Агент работает в Linux-контейнере, а часть инструментов существует только
на машине разработчика (например, платформа и конфигуратор 1С на Windows).
Мост даёт агенту ровно те команды, которые внесены в белый список.

- **Модель** (`internal/localbridge/bridge.go`): инструмент — имя,
  описание, шаблон argv с подстановками `{{аргумент}}`, описание аргументов
  (регулярное выражение, обязательность, значение по умолчанию), рабочий
  каталог, таймаут и признак подтверждения. Исполняемый файл не может быть
  подстановкой.
- **Подстановка**: значение аргумента целиком становится одним элементом
  argv, оболочка не используется. Без регулярного выражения значение не
  может содержать управляющие символы и начинаться с `-`; регулярное
  выражение проверяет значение целиком; длина ограничена 1024 символами.
- **Вызов**: инструмент с подтверждением ждёт решения человека до 5 минут
  (`agctl dev bridge pending`, `approve`, `deny`). Затем команда
  выполняется через `exec.Command` без оболочки, с таймаутом (по умолчанию
  2 минуты), вывод обрезается до 64 КиБ на поток.
- **Журнал** `logs/bridge.log`: события ожидания, отказа, истечения
  времени и вызова с argv, кодом выхода и длительностью; вывод команд не
  пишется. Сервер дополнительно пишет аудит в SQLite.
- **Сеть**: контейнер обращается к `http://host.docker.internal:<порт UI>`.
  В Docker Desktop это loopback хоста; в Docker Engine на Linux этот адрес
  указывает на шлюз `docker0`, поэтому сервер поднимает второй слушатель
  на этом IP и отдаёт на нём только пути моста.
- **Клиент в контейнере** (`cmd/agctl-guest/bridge.go`,
  `internal/localbridge/client.go`): `agctl bridge list`, `agctl bridge call
  ИНСТРУМЕНТ k=v …` и `agctl bridge mcp` — MCP-сервер «Мост к хосту» по
  stdio. Адрес и токен берутся из окружения или из `bridge.json`. Скилл
  `agctl-host-bridge` описывает агенту доступные инструменты.

Белый список по умолчанию даёт профиль организации
(`local/bridge-tools.yaml`); `dev init` копирует его в `dev.yaml`, дальше
разработчик правит свой файл.

### 6.7 Чем локальный режим отличается от серверного

Серверные модули не подключены: нет регистрации (`POST /api/register`
отвечает 405), ролей, лаунчера разработчика, админ-панели, prewarm,
autosave. Остальные отличия — проверки
`s.isLocal()` в ядре (12 мест в 8 файлах):

| Где | Что |
|---|---|
| `projects.go`, `handleProjectDelete` | 409: папки с диска из интерфейса не удаляются |
| `project_mcp.go` | MCP-сервер «Мост к хосту» виден только локально |
| `local.go`, `localChatExtras` | `/workspace` — папка разработчика; доступы и мост — только владельцу |
| `project_files.go`, `/api/me` | файлы проекта не отдаются (404): они и так на машине; консоль «Возможности» прячет блок «Файлы» |
| `local_ui.go` | смена папки проектов из лаунчера |
| `server.go` | регистрация локальных маршрутов |

Вне `internal/server` отличия задаются данными: `ChatSpec.Local` убирает
плагин «Кабинет», переменная `AGCTL_LOCAL_MODE=1` заставляет плагин
`chat-session-files` показывать только подпапки текущей папки проектов,
`--chat-ttl-min 720` не даёт контейнеру уснуть в течение рабочего дня.

### 6.8 Безопасность локального режима

- Сервер слушает только loopback: `devInit --addr` и `devServe` отвергают
  любой другой адрес; исключение — слушатель моста на `docker0` (Linux), и
  на нём доступны только пути моста.
- Вход — одноразовый токен из файла 0600; учётной записи и пароля у
  владельца нет; сессии браузера хранятся в виде хешей.
- Обработчики лаунчера требуют cookie-сессии и одного источника для
  изменений; значения секретов в ответах не возвращаются.
- Мост: argv без оболочки, проверка значений, подтверждение, журнал, аудит,
  таймауты и ограничение вывода; команды — только из белого списка в файле
  разработчика.
- Папка проектов выбирается явно; весь домашний каталог и корень запрещены.
- Агент работает с правами разработчика в GitLab и Jira. Правило работы —
  ветки `agent/*`, merge request вместо push в `main`, слияние делает
  человек.

### 6.9 Несколько рабочих мест и лаунчер v2

> Этап 1 предложения `docs/proposals/2026-11-18-launcher-v2.md`; ветка
> `agent/launcher-v2-slots`, в `main` ещё не вмержено.

**Рабочее место — это слот** (карточка `developer-multi-containers`): та же
модель, что у серверного лаунчера developer'а. Слот — контейнер со своим
томом и домашним каталогом dsh; ключ рантайма `chatKey{uid, slot}`, образ
слота — в `settings` (`chat-image-u<ID>[-s<N>]`), лимит — `--launcher-slots-max`
(в локальном режиме по умолчанию 8, на сервере — 3). Лаунчер v2 добавляет
поверх слота то, что нужно локальному режиму: имя, id для адреса и папки
хоста — таблица `places` (миграция `014`, ключ `(user_id, id)`, слот
уникален у пользователя, без внешнего ключа на `users`).

**Основное** место (`main` в API) — слот 0: папка и образ из `dev.yaml`,
адрес `/chat/`, имена контейнера и хранилища прежние. **Дополнительные**
места занимают младший свободный слот 1…N−1. При удалении места слот
освобождается, а его данные (`data/chats/u1s<N>`: dsh-home с сессиями,
скиллами и настройками) переименовываются в `u1s<N>.deleted-<время>` —
следующее место на этом слоте начинает с чистого dsh-home. Папки хоста не
трогаются.

| Что | Основное место | Дополнительное место `<id>` на слоте `N` |
|---|---|---|
| Ключ рантайма (`chatKey`) | `{owner, 0}` | `{owner, N}` |
| Контейнер | `agctl-chat-<хеш>-u1` | `agctl-chat-<хеш>-u1-s<N>` |
| dsh-home | `data/chats/u1/dsh-home` | `data/chats/u1s<N>/dsh-home` |
| Образ | `dev.yaml` (копия в `settings`, `chat-image-u1`) | `settings`, `chat-image-u1-s<N>` |
| Адрес чата | `/chat/` | `/p/<id>/` (тот же шлюз `chatProxyAt` с другим префиксом; ресурсы dsh относительные, поэтому работают под любым префиксом) |
| Папки | одна → `/workspace` | одна → `/workspace`; несколько → `/workspace` — служебный каталог agctl, каждая папка → `/workspace/<имя>` (точки монтирования в папках пользователя не создаются) |

Ключ модели и доступы общие для всех мест; провайдер и файлы доступов
пишутся в dsh-home каждого места при его старте.

API лаунчера (`internal/server/local_places.go`, только владелец, изменения —
только с того же источника):

| Маршрут | Что делает |
|---|---|
| `GET /api/local/ui/places` | все места: состояние, образ, папки и куда они видны в контейнере, ревизия, адрес чата, dsh-home, ход подготовки |
| `POST /api/local/ui/places` | создать: имя, id (иначе из имени), образ, папки (проверка как у папки проектов: существует, не `$HOME` целиком, не корень) |
| `PUT /api/local/ui/places/{id}` | изменить с ревизией (тело `revision` или `If-Match`); устаревшая — 409. У основного места меняются папка и образ в `dev.yaml` |
| `DELETE /api/local/ui/places/{id}` | остановить, удалить запись и образ слота; данные слота — в архив `u1s<N>.deleted-<время>` (путь в ответе `archived`) |
| `POST /api/local/ui/places/{id}/start\|restart\|stop`, `GET …/logs` | управление контейнером места; логи без токенов загрузки dsh |
| `GET /api/local/ui/fs?path=` | подкаталоги внутри домашнего каталога (дерево выбора папок), признак git, можно ли выбрать |
| `POST /api/local/ui/fs/dialog` | системный диалог выбора папки (Finder на macOS через osascript, zenity/kdialog на Linux, FolderBrowserDialog на Windows); отмена различима, нет утилиты — 409. Новое место без выбранных папок получает `<папка проектов>/<id>` — форма всегда валидна |
| `POST /api/local/ui/reveal` | «Показать в Finder» (`open -R`) или «Открыть в VS Code» (`code`) на машине разработчика — только внутри папок и dsh-home мест |
| `GET /api/local/ui/models` | провайдеры и модели платформы, статус ключа каждого; ключ меняется через доступы |
| `GET/POST /api/local/ui/presets`, `PUT/DELETE …/presets/{id}` | пресеты возможностей: набор MCP платформы + скиллы каталога профиля + места применения, ревизия (409 на устаревшую). agctl материализует пресет в dsh-home мест — `.agent-presets/agctl-<id>/agent.cordis.yml` и `skills/<имя>/…` — и при каждом старте места; в dsh пресет просто выбирается при создании сессии |
| `GET /api/local/ui/events` | поток событий (SSE): тема и номер при каждом изменении мест, пресетов, доступов, образа; обе копии интерфейса перечитывают данные сами |
| `GET /launcher`, `GET /launcher/embed/<places\|presets\|models\|secrets>?ws=<id>` | полный лаунчер и встроенный режим без шапки — для будущих табов правой панели dsh |

Интерфейс (`web/src/LocalLauncher.tsx`, `PlacesView.tsx`, `ModelsView.tsx`,
`SecretsView.tsx`): вкладки «Рабочие места» (карточки, мастер с деревом папок и
выбором образа, Finder и VS Code, логи), «Модели», «Доступы».

Страницы SPA в локальном режиме помечены `window.__AGCTL_LOCAL__`
(`injectLocalModeBoot` в `internal/server/htmlscan.go`; корень `/` и `/launcher`):
без сессии вместо серверной формы логина показывается экран «выполните
`agctl dev open`» — учётных паролей в локальном режиме нет. В серверном режиме
флаг не ставится, форма логина легитимна.

Тема оформления переключается кнопкой в шапке лаунчера (`web/src/theme.ts`):
тёмная по умолчанию, выбор — в `localStorage` (полная вкладка и встроенные
табы dsh — тот же origin — показывают одно и то же). Атрибут `data-theme`
ставится только из лаунчера, поэтому страницы серверного режима без него
выглядят как раньше.

## 7. Сети и порты: сводка по всем режимам

| Режим | Откуда → куда | Протокол и порт | Что защищает |
|---|---|---|---|
| все | браузер → agctl | HTTP 8929 (сервер) или 8930 (локальный), на сервере через обратный прокси с HTTPS | cookie `agctl_session` (HttpOnly, SameSite=Lax, Secure при TLS) |
| сервер, локальный | agctl → dsh в контейнере | HTTP, WebSocket, SSE: `127.0.0.1:<свободный порт>` → контейнер 3080 | порт опубликован только на loopback; токен загрузки dsh подставляет шлюз |
| сервер, локальный | agctl → Docker | Docker Engine API: unix-сокет (`/var/run/docker.sock`, на macOS `~/.docker/run/docker.sock`) или named pipe на Windows | права пользователя ОС на сокет |
| сервер | разработчик → sshd контейнера | SSH: `127.0.0.1:<порт>` хоста → контейнер 2222, снаружи — через туннель или VPN | только ключи; без перенаправлений портов |
| сервер, локальный | контейнер → провайдер модели, GitLab, Jira | HTTPS 443 (как в URL провайдера); DNS провайдера закреплён в `/etc/hosts` | ключ модели — в `.credentials.yaml` домашнего каталога dsh |
| сервер с `Config.EgressAllowlist` (флага нет) | контейнер → интернет | только DNS 53 и шлюз сети (хост) | цепочка правил в `DOCKER-USER` |
| локальный | контейнер → мост | HTTP: `host.docker.internal:8930`, на Linux — IP `docker0`:8930 | токен моста; только пути моста на втором слушателе |
| локальный | CLI на хосте → фоновый процесс | HTTP `127.0.0.1:8930` | токен управления |
| локальный, лаунчер v2 | браузер → чат дополнительного места | HTTP `127.0.0.1:8930/p/<id>/` → контейнер места 3080 | cookie владельца; dsh-auth с путём `/p/<id>/` |
| k8s | ingress → Service `agctl` | HTTP 80 → под 8929 | NetworkPolicy `agctl-gateway` (ingress-nginx и своё пространство имён) |
| k8s | шлюз → под пользователя | HTTP `chat-<под>.<ns>.svc.cluster.local:80` → 3080 | NetworkPolicy пода: вход к 3080 только от подов шлюза |
| k8s | шлюз → kube-apiserver | HTTPS | Role `agctl-runtime` (поды, сервисы, PVC, секреты, network policies, `pods/log`, `pods/exec`) |
| k8s | разработчик → sshd пода | SSH: `--k8s-ssh-host:<NodePort>` → 2222 | только ключи; источник не ограничен NetworkPolicy |
| ax | шлюз → ax-server | gRPC без TLS, 8080 | сеть кластера |
| ax | шлюз → маршрутизатор Substrate → раннер | HTTP 80 (или HTTPS 443) с заголовком `ate-target-actor` → раннер 80 → dsh 3080 | маршрутизатор Substrate |
| ax | раннер → шлюз | HTTP `<PublicURL>/ax/provider-config/<task>` | токен раннера (Bearer) |
| ax с `--ax-inject-llm-key=0` | песочница → провайдер модели | HTTPS через egress-шлюз Substrate, который подставляет ключ | ключ не попадает в песочницу |

### 8.1 Схема SQLite

Миграции `internal/store/migrations` (применяются по порядку при открытии
базы):

| `008_local_connectors` | таблица старого WSS-коннектора (удалена миграцией `013`) |
| `009_settings` | `settings` — ключ-значение: провайдер платформы (зашифрован), SSH-ключи, желаемые образы, MCP и компоненты проектов, лимиты пользователей, токен раннера AX |

| `014_places` | рабочие места лаунчера v2 поверх слотов: id, слот, имя, папки хоста, ревизия |

Внешние ключи на `users` есть у `sessions`, `workspaces` и `secrets`; у
`settings`, `audit_log` и `places` их нет. Поэтому в локальном режиме
используются только `settings`, `audit_log` и `places` (рабочие места
лаунчера v2), а `users` и `sessions` остаются пустыми.

### 8.2 Файлы на диске

Серверный дом `$AGCTL_HOME` (по умолчанию `~/.agctl`, в кластере
`/var/lib/agctl`):

| Путь | Содержимое |
|---|---|
| `agctl.db` (+ `-wal`, `-shm`) | SQLite |
| `secrets.key` (0600) | мастер-ключ AES-256-GCM |
| `chats/u<ID>/work` | `/workspace` пользователя: проекты, git с автосохранением |
| `chats/u<ID>/dsh-home` | `/home/dsh`: сессии, настройки, плагины, скиллы, `.credentials.yaml`, `.agctl/` |
| `profiles/` | профили организаций по имени |
| `repos/` | bare-репозитории рабочих мест версии до 3 |

Локальный дом `~/.agctl-dev` описан в разделе 6.1.

### 8.3 Где живут секреты

| Секрет | Локальный режим | Сервер | Kubernetes | AX |
|---|---|---|---|---|
| ключ модели платформы | хранилище ОС → окружение процесса → SQLite (зашифрован) | `.env` / окружение → SQLite (зашифрован) | Secret `agctl-llm` шлюза | как в k8s |
| ключ модели в рабочем месте | `.credentials.yaml` (0600) в домашнем каталоге dsh | то же | Secret пода, переменная по `secretKeyRef` | конфигурация при загрузке либо подстановка на egress |
| доступы GitLab и Jira | хранилище ОС → окружение контейнера и файлы `/home/dsh/.agctl` | `--dev-env` из `.env` хоста (только developer) | `DevEnv` в окружении пода | окружение задачи |
| пароли пользователей | нет | argon2id в `users` | то же | то же |
| сессии | sha256 в `local-sessions.json` | `sessions` в SQLite | то же | то же |

### 8.4 Ключ модели в рабочем месте

Docker-бэкенд (локальный и серверный режимы) не кладёт ключи модели в
окружение контейнера (`dockerrt.containerEnv`): иначе они были бы видны в
`docker inspect` и `/proc/*/environ` и наследовались бы MCP-серверами,
git-хуками и npm-скриптами. dsh читает ключ из `.credentials.yaml`;
у плагина `dsh-credentials-local` значение из файла главнее окружения.
Ограничение, описанное в документации самого dsh: процессы агента
работают тем же пользователем, поэтому файл агент прочитать может.
Полностью скрыть ключ от агента позволяет только подстановка ключа вне
песочницы — сейчас это режим AX с `--ax-inject-llm-key=0`.

## 9. Образ рабочего места и домашний каталог dsh

Образа два — по одному на режим (карточка `guest-image-flavours`): локальный
`agctl-dsh*` с guest-бинарём только с мостом (`bridge`) и серверный
`agctl-dsh-server*` с guest `-tags server` (`ax-runner`, `init-chat-home`).
Контекст общий (`internal/assets/image`), вариант выбирается build-arg
`GUEST_FLAVOR=local|server`; контекст встроен в бинари, поэтому собрать
образ можно и без исходников:

| Стадия | Содержимое |
|---|---|
| `base` | `node:22-bookworm-slim`, python3, pip, pytest, make, g++, git, openssh-server, iptables |
| `dsh` | `@deepseek-ai/dsh` закреплённой версии (сейчас 0.2.2-rc.3, тег образа `0.2.2`), git-идентификатор агента |
| `mcp-warm` | прогретый кэш npx для MCP-серверов DuckDuckGo, Context7, GitLab, Playwright |
| `runtime` | кэш MCP, LibreOffice Impress (превью презентаций), ripgrep, fd, jq, sqlite3, клиенты БД, `glab`, `jira-cli`, `uv`/`uvx`, бинарь `agctl-guest` своего варианта как `/usr/local/bin/agctl` (build-arg `GUEST_FLAVOR`), скелет домашнего каталога, `entrypoint.sh`, обёртка `ax-task-runner` (только серверный вариант), `HEALTHCHECK` (`agctl-dsh-net health` раз в 30 секунд) |
| `flavors/web` | `FROM agctl-dsh` + Chromium через Playwright |

Цепочка имён локальных образов: `agctl-dsh:0.2.2` (базовый),
`agctl-dsh-nossh:0.2.2` (без sshd), `agctl-dsh-web:0.2.2` (вкус web),
`agctl-dsh[-web]-<профиль>:0.2.2` (надстройка профиля),
`agctl-dsh-<профиль>-<вкус>:0.2.2` (вкус профиля). Серверные:
`agctl-dsh-server:0.2.2`, `agctl-dsh-server-nossh:0.2.2` и надстройка
`agctl-dsh-server-<профиль>:0.2.2`; k8s/ax берут образ из реестра
(`--k8s-image`/`--ax-image`, по умолчанию — `--image`).
В репозитории их собирает `make img_build [PROFILE=<id>]` (оба семейства)
или `make img_build_server` (только серверные) и публикует
`make img_push REGISTRY=…`. На машине без исходников локальный режим
сначала пробует `docker pull`, а если реестр образа не знает, собирает
недостающие ступени (`dockerrt.BuildDevImage`); для этого нужен
`agctl-guest-linux-<arch>` рядом с бинарём или в `../lib/agctl`
(`findLinuxBinary`). Сервер тем же кодом (`dockerrt.EnsureImage`,
`GuestServer`) собирает базовый образ и надстройку профиля, но ищет
серверный бинарь `agctl-guest-server-linux-<arch>` — локальный он не
подставит, чтобы не получить образ без `ax-runner`/`init-chat-home`
(`findServerLinuxBinary`).

`entrypoint.sh` при старте контейнера заполняет пустой домашний каталог
скелетом, при наличии ключа разработчика запускает sshd на 2222 и
запускает `dsh web --host <IP eth0> --port 3080`.

проведена регистрацией, а не пакетами.

### 10.3 Сильные стороны

- **Одно ядро для всех режимов.** Самая сложная часть системы — жизненный
  цикл рантайма, шлюз чата, подготовка домашнего каталога dsh, MCP и
  образ — написана один раз и проверена во всех режимах. Локальный режим
  добавляет около 4 150 строк поверх неё (`cmd/agctl`, `localmode`,
  `localbridge` и локальные файлы сервера).
- **Явная граница между режимами.** Серверные функции подключаются
  модулями; оставшиеся проверки `isLocal()` собраны в 10 местах и описаны в
  разделе 6.7. Тест проверяет отсутствие серверных маршрутов в локальном
  режиме.
- **Адаптеры рантайма за одним контрактом.** Docker, Kubernetes и AX
  взаимозаменяемы для сервера; различия в сети и хранении изолированы в
  `internal/runtime/*`.
- **Аккуратное обращение с секретами.** Шифрование в SQLite, хранилище ОС
  локально, ключ модели вне окружения контейнера, файлы доступов 0600,
  ключи в Kubernetes — через Secret, подстановка ключа на egress в AX.
- **Профиль как данные.** Организация подключается без изменения кода;
  тест следит, чтобы ядро оставалось нейтральным.
- **Проверки.** Около 12 400 строк тестов, живые e2e-сценарии для
  локального режима, сервера, SSH и kind-кластера, CI на трёх ОС, gitleaks.

### 10.4 Слабые места и риски

- **Функции, реализованные, но не подключённые к CLI.** Egress-allowlist
  контейнеров, пул prewarm и квоты LiteLLM целиком написаны и покрыты
  тестами (`egress.go`, `chat_prewarm.go`, `litellm.go`), но команда `serve`
  не выставляет поля `Config.EgressAllowlist`, `ChatPrewarmN`,
  `LiteLLMQuotas`, `LiteLLMAdminURL`, `LiteLLMAdminKey`, а комментарии в
  коде ссылаются на «opt-in флаг serve», которого нет. Так было и до
  разделения бинарей. В итоге в серверном режиме эти механизмы выключены
  без возможности включить их без изменения кода.
- **Крупные файлы.** `internal/server/chat.go` (около 1 000 строк),
  `server.go` (около 930) и `cmd/agctl/dev.go` (около 1 300) совмещают
  несколько ответственностей: в `chat.go` — менеджер рантаймов, шлюз и
  страницы ожидания; в `server.go` — маршруты, фоновые задачи, сверка
  рантаймов, валидация провайдера и обработчик конфигурации AX; в `dev.go`
  — все подкоманды `agctl dev`. Их стоит разделить по ответственности.
- **Наследие версии до 3 — удалено** (карточка `legacy-workspace-code-cleanup`):
  маршруты `/api/workspaces*`, `/api/templates`, `/api/kits`, заявки на
  рабочие места, шлюз `/w/{id}/`, опросчик Jira, store-модели `workspaces`/
  `workspace_requests`/`jira_runs` и модуль `legacy-workspaces`. Схема
  прежних таблиц остаётся в миграциях (append-only): миграции `002`–`007`
  не откатываются.
- **Модель данных локального режима.** Локальный режим всё ещё открывает
  SQLite с полной серверной схемой, хотя пользуется только двумя таблицами.
  Это осознанное решение (общий код ядра работает с `settings` и
  `audit_log`), но схема несёт лишние для локального режима таблицы.
- **mTLS к маршрутизатору AX** — закрыто: адаптер отдаёт TLS-клиент в
  `ChatHandle.TLSConfig`, и обратный прокси чата ходит с ним (копия
  `tls.Clone`); без mTLS — общий `proxyTransport`. Живой проверки на
  маршрутизаторе Substrate ещё не было.
- **Сетевые политики кластера.** Правило NetworkPolicy для SSH (2222) не
  ограничивает источник; исходящий трафик подов пользователей не
  ограничен; базовая политика шлюза пропускает вход только из
  `ingress-nginx` и своего пространства имён, поэтому запрос раннера AX к
  `/ax/provider-config` может потребовать дополнительного правила;
  пример `deploy/ax/egress-policy.example.yaml` расходится с форматом
  `credentialUri`, который формирует код.
- **SSH в поде от root.** С включённым SSH под Kubernetes работает от root
  с дополнительными capabilities.
- **Ключ модели доступен агенту.** Во всех режимах, кроме AX с подстановкой
  на egress, агент может прочитать `.credentials.yaml` (раздел 8.4).
- **Windows живьём не проверен.** Локальный режим на Windows пока
  проверен только сборкой и тестами в CI.

Релизы собирает goreleaser по тегу `v*` (`.goreleaser.yaml`): архивы
`agctl_<os>_<arch>`, `agctl-server_<os>_<arch>`, `agctl-guest_linux_<arch>`
(локальный guest), `agctl-guest-server_linux_<arch>` (серверный guest) и
`checksums.txt`; версия, коммит и дата сборки подставляются флагами
компоновщика. Установщики `bin/install.sh` и `bin/install.ps1` ставят
`agctl` и оба `agctl-guest`, сверяют SHA-256 и умеют ставить комплект
организации из приватного репозитория профиля (архив с `agctl`, обоими
`agctl-guest` и профилем; его собирает `bin/release.sh`
репозитория профиля).

CI (`.github/workflows/ci.yml`): `go vet` и `go test` на Linux, macOS и
Windows, сборка SPA, gitleaks; по тегу — пробная сборка релиза.
`dsh-bump.yml` еженедельно проверяет новую версию dsh: PR с подъёмом пина
по `latest` (rc/stable) пропускается через `bin/e2e-smoke.sh`; вторым
конвейером собирается образ на свежем dist-tag `next` (`--build-arg
DSH_VERSION`, пин не двигается) и гоняются тесты плагинов и
`bin/e2e-first-session.sh` — при провале заводится issue, автомержа нет.

Живые сценарии (`bin/`): `e2e-local-mode.sh` (локальный режим целиком:
init, доступы, запуск, вход, папка проектов, мост, обновление и откат),
`e2e-smoke.sh` (сервер со стабом модели: роли, проекты, autosave, живой
запрос к модели), `e2e-cabinet.sh`, `e2e-ssh.sh`, `e2e-first-session.sh`,
`e2e-k8s-kind.sh` (kind-кластер), браузерные сценарии `tests/e2e-ui`.

## 12. Состояние и открытые вопросы
