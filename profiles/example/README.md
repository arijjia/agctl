# Профиль организации — пример

Профиль — это всё, чем одна организация отличается от другой: логотип и две
фразы, модели, инструменты агента, образ рабочего места. Ядро agctl от
организации не зависит; организация подключается этим каталогом.

Скопируйте каталог, переименуйте (`id` в `profile.yaml` = имя каталога) и
правьте. Секретов в профиле нет и быть не должно.

## Что где лежит

| Путь | Что это | Кто читает |
|---|---|---|
| `profile.yaml` | Настройки организации: бренд, модели, сеть, сценарии, образы. Каждое поле прокомментировано в файле | agctl и agctl-server при старте |
| `assets/logo.png` | Логотип (PNG, квадрат) | `brand.logo` |
| `catalog/<id>/` | Инструменты агента: скиллы и MCP-серверы. Из них разработчик собирает пресеты | лаунчер → «Пресеты», консоль воркспейса |
| `local/bridge-tools.yaml` | Команды на компьютере разработчика, разрешённые агенту (локальный режим) | agctl при старте |
| `image/Dockerfile` | Надстройка образа рабочего места: пакеты и CLI для всех сотрудников | `images.dockerfile` |

## Что настраивает организация

1. **Бренд** — `brand` в `profile.yaml`: логотип, название над левой панелью
   чата (`brand.name`), приветственная фраза (`brand.tagline`).
2. **Модели** — `llm`: основной провайдер и дополнительные. Ключи — не здесь:
   в профиле только имя переменной.
3. **Инструменты** — `catalog/`, `local/bridge-tools.yaml`, `image/Dockerfile`.

## Как подключить инструмент

Инструменты бывают четырёх видов. Выберите по тому, что нужно агенту.

| Нужно | Вид | Куда положить |
|---|---|---|
| Научить агента процедуре (чек-лист, регламент, как работать с вашей системой) | Скилл | `catalog/<id>/files/.dsh/skills/<имя>/SKILL.md` |
| Дать агенту новые действия (запросы к API, поиск по базе знаний) | MCP-сервер | `catalog/<id>/manifest.json`, блок `mcp` |
| Разрешить команду на компьютере разработчика | Команда моста | `local/bridge-tools.yaml` |
| Поставить программу в контейнер | Пакет образа | `image/Dockerfile` |

### Скилл

Скилл — папка с файлом `SKILL.md`: инструкция, которую агент читает, когда
задача подходит под описание. Пример — `catalog/code-review/`.

```
catalog/code-review/
  manifest.json                              название и описание пакета
  files/.dsh/skills/code-review/SKILL.md     сам скилл
```

Требования к `SKILL.md`:

- в начале — блок с `name` (совпадает с именем папки) и `description`;
- `description` отвечает на вопрос «когда это применять» — по нему агент
  решает, открывать ли скилл;
- в теле — шаги в повелительном наклонении, с командами, которые можно
  выполнить; вспомогательные скрипты и файлы кладите рядом в ту же папку.

### MCP-сервер

MCP-сервер добавляет агенту инструменты. Сервер запускается внутри
контейнера рабочего места по stdio. Пример — `catalog/docs-memory/`.

```json
{
  "schema": 1,
  "id": "docs-memory",
  "title": "Память агента (MCP)",
  "description": "Что умеет сервер — одной фразой, её видит разработчик",
  "mcp": {
    "server_name": "docs-memory",
    "command": "npx",
    "args": ["-y", "@modelcontextprotocol/server-memory"],
    "env": ["DOCS_MEMORY_TOKEN"]
  }
}
```

| Поле | Что это |
|---|---|
| `id` | Идентификатор пакета = имя каталога. Строчная латиница, цифры, дефис |
| `title`, `description` | Подпись и пояснение в конструкторе пресетов |
| `mcp.server_name` | Имя сервера у агента: инструменты видны как `mcp__<server_name>__<инструмент>` |
| `mcp.command`, `mcp.args` | Как запустить сервер в контейнере: `npx`, `uvx` или программа из `image/Dockerfile` |
| `mcp.env` | Имена переменных доступа, которые нужны серверу. Значения разработчик вводит в лаунчере («Доступ»); в профиле значений нет |

Требования к серверу: транспорт stdio; не требует интерактивного входа;
если пакет тянется из сети при первом запуске — добавьте его хост в
`egress.allow` или поставьте заранее в `image/Dockerfile`.

### Команда моста

Мост — белый список команд на компьютере разработчика (локальный режим):
то, что живёт не в контейнере. Формат и правила безопасности описаны в
шапке `local/bridge-tools.yaml`.

### Пакет образа

Всё, что должно быть в контейнере у каждого сотрудника, — в
`image/Dockerfile`. Он собирается поверх базового образа agctl. Базовый
образ agctl скачивается из реестра образов (`images.registry` в
`profile.yaml`, по умолчанию `ghcr.io/arijjia`), надстройка собирается на
машине разработчика за минуты — или тоже скачивается, если организация
публикует образы в свой реестр (вместе с базовыми `agctl-dsh`) и указывает
его в `images.registry`.

## Как это попадает к агенту

1. Разработчик открывает лаунчер → «Пресеты» и собирает пресет: отмечает
   MCP-серверы и скиллы из `catalog/`.
2. Перезапускает рабочее место.
3. В чате выбирает пресет в списке режимов у поля ввода.

Скиллы пресета видны только сессиям с этим пресетом. Пакет `catalog/`
можно также поставить в отдельный воркспейс из консоли «Возможности».

## Проверить профиль

```sh
agctl dev init --profile-dir ./profiles/example --yes   # проверит profile.yaml
agctl dev up
agctl dev paths                                          # все пути, порты и контейнеры
```

Ошибка в `profile.yaml` или в `manifest.json` пакета называется при старте
с именем поля.
