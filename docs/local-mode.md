# Локальный режим (`agctl dev`)

Платформа на машине разработчика: тот же интерфейс, плагины и модели, что на
сервере, но для одного человека и рядом с его файлами. Рабочее место агента —
контейнер на локальном Docker; агент видит только папку проектов, которую вы
ему дали, и команды хоста из белого списка (мост к хосту).

Решения и их причины — карточка `local-mode-v2-container-bridge` в бэклоге.

## Что нужно

- **Docker**: Docker Desktop (macOS / Windows с WSL2), Docker Engine (Linux),
  либо Rancher Desktop / Podman Desktop / Colima.
- **Бинарь `agctl`** под вашу ОС (выдаёт команда платформы). Из исходников —
  `make install`; для другой машины — `make release_local`, и рядом с бинарём
  положить `agctl-linux-<arch>`: тогда `dev up` соберёт базовый образ сам,
  если его нет в реестре. Подробно — [cli-and-build.md](cli-and-build.md).
- 8 ГБ ОЗУ, ~15 ГБ диска (образ с браузерами — 2–3 ГБ).
- Доступ к реестру образов организации: `docker login <реестр>`.

## Быстрый старт

```bash
agctl dev init        # профиль и папка проектов
agctl dev up          # платформа; в браузере откроется лаунчер
agctl dev doctor      # если что-то не так
agctl dev down        # остановить (сессии и настройки сохраняются)
```

**Лаунчер** (http://127.0.0.1:8930/launcher, открывается после входа):

- **Доступы** — ключ модели, адрес и токен GitLab, адрес, логин и токен Jira,
  свои переменные. Секреты уходят в хранилище ОС, обратно на страницу не
  возвращаются (видно только «задан / не задан»). Пока ключа модели нет,
  лаунчер открывается на этой вкладке.
- **Рабочее место** — образ из профиля (базовый, веб, 1С) с отметкой «есть
  на машине»; «Запустить» скачивает недостающий образ из реестра или
  собирает его здесь же (10–20 минут, прогресс на странице), затем
  поднимает контейнер. Изменили доступы или образ у работающего места —
  появится «Перезапустить».
- **Открыть чат** — dsh. Если образ на машине и ключ задан, рабочее место
  стартует сразу при входе.

Всё это доступно и из терминала: `agctl dev init --cli` (мастер),
`agctl dev secrets …`.

`agctl dev up ~/src/проект` — поднять с другой папкой (она станет
`/workspace` в контейнере). Повторный `up` с той же папкой просто откроет
браузер; с другой — попросит сначала `down`.

Вход без пароля: `up` открывает одноразовую ссылку входа. Потеряли вкладку —
`agctl dev open`. Регистрации и других пользователей в локальном режиме нет;
вы — разработчик (роль developer).

## Команды

| Команда | Что делает |
|---|---|
| `dev init [--profile ID] [--image REF] [--flavor web\|1c] [--workdir DIR] [--yes] [--cli]` | профиль и папка проектов; образ и доступы — в лаунчере (`--cli` — мастер в терминале) |
| `dev up [DIR] [--no-open] [--foreground]` | поднять в фоне (лог — `~/.agctl-dev/logs/serve.log`) |
| `dev down` | остановить платформу и контейнер |
| `dev status` | адрес, образ, папка, состояние рабочего места и моста |
| `dev open` | новая ссылка входа в браузере |
| `dev logs [-f]` | лог фонового процесса |
| `dev secrets list \| set ИМЯ [--stdin] [--plain] \| rm ИМЯ` | доступы |
| `dev bridge list \| pending \| approve ID \| deny ID \| log` | мост к хосту |
| `dev update [--image REF]` | обновить образ: бэкап → запуск → проверка → откат при сбое |
| `dev rollback [--restore-data]` | вернуть предыдущий образ (и данные dsh из бэкапа) |
| `dev doctor` | docker, образ, доступы, сеть до модели/GitLab/Jira, мост |

Дом режима — `~/.agctl-dev` (`AGCTL_DEV_HOME` переопределяет): `dev.yaml`
(настройки, без секретов), `data/` (база и dsh-home: сессии, настройки dsh),
`backups/`, `logs/`. Серверный `~/.agctl` и `~/.config/agctl/config.yaml` на
локальный режим не влияют.

## Доступы и секреты

Значения хранятся в **хранилище ОС**: Keychain (macOS), Диспетчер учётных
данных (Windows), Secret Service (Linux). Если его нет (Linux без
gnome-keyring, WSL) — в зашифрованном файле `~/.agctl-dev/secrets.enc`
(AES-GCM, ключ 0600 рядом). Несекретные значения (адреса, логины) — в
`dev.yaml`.

| Переменная | Что | Как задать |
|---|---|---|
| `AGCTL_LLM_API_KEY` | ключ модели | лаунчер → «Доступы», или `agctl dev secrets set AGCTL_LLM_API_KEY` |
| `GITLAB_URL` | адрес GitLab | `agctl dev secrets set GITLAB_URL` (несекретная) |
| `GITLAB_TOKEN` | личный токен GitLab (scope `api`, `write_repository`) | `agctl dev secrets set GITLAB_TOKEN` |
| `JIRA_URL`, `JIRA_USER` | адрес и логин Jira | несекретные |
| `JIRA_API_TOKEN` | личный токен Jira (PAT) | секрет |
| любое `ИМЯ` | ваши переменные (например ключ Tavily) | `agctl dev secrets set ИМЯ` |

В контейнер они попадают при старте рабочего места как переменные
окружения, плюс производные имена для штатных инструментов: `GITLAB_HOST`
(glab), `GITLAB_API_URL` + `GITLAB_PERSONAL_ACCESS_TOKEN` (MCP GitLab),
`JIRA_PERSONAL_TOKEN` / `JIRA_USERNAME` (MCP Jira). Ключ модели в контейнер
**не** передаётся — его получает платформа как провайдера. После смены
доступа: `agctl dev down && agctl dev up`.

**Как агент ими пользуется.** Инструмент bash в dsh запускает команды агента
с вычищенным окружением: переменные с `KEY`/`TOKEN`/`SECRET`/`PASSWORD` в
имени до него не доходят. Поэтому платформа дополнительно кладёт доступы
файлами в dsh-home (`/home/dsh/.agctl/`, права 0600; **не** в `/workspace` —
это ваша папка проектов): `git` пушит в GitLab по токену (`GIT_CONFIG_GLOBAL`
→ credential helper), `glab` настроен на ваш GitLab (`GLAB_CONFIG_DIR`),
остальное агент подгружает из `$AGCTL_CREDENTIALS_ENV` (скилл
`agctl-workspace-access` ему это объясняет, не раскрывая значений).
MCP-серверы GitLab/Jira получают доступы напрямую из пресета воркспейса.

Ни в образ, ни в логи, ни в git секреты не попадают. Видеть env контейнера
(`docker inspect`) может только тот, у кого есть доступ к Docker на этой
машине, — то есть вы.

## Что внутри контейнера

**Базовый образ** (для всех): dsh, git, Node 22, Python 3 + pip + pytest, uv
и uvx, glab (GitLab CLI), jira-cli, ripgrep, fd, jq, sqlite3, клиенты
PostgreSQL / MySQL / Redis, LibreOffice Impress (превью pptx), MCP-серверы
DuckDuckGo, Context7, GitLab, Playwright (прогреты).

**Вкус `web`** (`agctl-dsh-web`): + Playwright с Chromium — агент открывает
страницы, кликает, делает скриншоты, гоняет e2e.

**Вкусы организации** — в её профиле (`image/flavors/<вкус>/Dockerfile`,
собираются поверх надстройки профиля как `agctl-dsh-<профиль>-<вкус>`).

MCP-серверы включаются по воркспейсу: «Воркспейсы: возможности» → MCP.
Доступы GitLab/Jira подставляются из ваших секретов автоматически. Jira-MCP
(`mcp-atlassian`) ставится через uvx при первом включении; без прямого
доступа к PyPI задайте зеркало: `agctl dev secrets set UV_INDEX_URL --plain`.

## Мост к хосту

Агент работает в Linux-контейнере, а некоторые программы есть только на
вашей машине (например, платформа и конфигуратор на Windows). Мост даёт
агенту **только** команды из белого списка в `~/.agctl-dev/dev.yaml`:

```yaml
bridge:
  tools:
    - name: config_check                  # [a-z0-9_]
      description: Проверка конфигурации базы (только чтение)
      command: ["ibcmd", "infobase", "config", "check", "--db-path={{db}}"]
      args:
        db: {description: "путь к базе", required: true}
      timeout_sec: 900
    - name: config_import
      description: Загрузить выгрузку в тестовую базу (изменяет базу)
      command: ["ibcmd", "infobase", "config", "import", "--db-path={{db}}", "{{dir}}"]
      args:
        db: {required: true}
        dir: {required: true, pattern: '[A-Za-z]:\\.+'}   # своя проверка значения
      confirm: true                        # ждать подтверждения человека
```

Правила безопасности:

- команда запускается **без shell**: значение аргумента целиком уходит в один
  элемент argv, `; rm -rf` не исполнится;
- значения проверяются: по умолчанию без управляющих символов и без ведущего
  `-` (нельзя подсунуть опцию); `pattern` — своя регулярка;
- `confirm: true` — вызов ждёт вашего решения: `agctl dev bridge pending`,
  затем `approve ID` или `deny ID` (5 минут, потом отказ);
- каждый вызов — в журнале `~/.agctl-dev/logs/bridge.log` (без вывода
  команды) и в аудите платформы.

Профиль организации может дать белый список по умолчанию
(`local/bridge-tools.yaml` в профиле) — `dev init` положит его в `dev.yaml`.

Изнутри контейнера агент вызывает мост командой
`agctl bridge call ИНСТРУМЕНТ имя=значение` (скилл `agctl-host-bridge`
подсказывает ему список) или как MCP-сервер «Мост к хосту» в консоли
воркспейса.

На Linux (Docker Engine) мост слушает дополнительно адрес шлюза `docker0` —
только пути моста; интерфейс и вход остаются на `127.0.0.1`.

## Обновления

Версии dsh и инструментов выбирает команда платформы: новый dsh сначала
проходит e2e-проверки, потом публикуется образ. У вас:

```bash
agctl dev update                 # тот же тег заново (новая сборка) или образ профиля
agctl dev update --image <реестр>/agctl-dsh-web-org:0.2.3
agctl dev rollback               # вернуть прошлый образ
agctl dev rollback --restore-data
```

`update` делает: скачивание → остановку → **бэкап dsh-home** (сессии,
настройки, хранятся 3 последних в `~/.agctl-dev/backups`) → запуск на новом
образе (управляемые слои — бренд, плагины, провайдер — перезасеваются, ваши
настройки не трогаются) → проверку, что рабочее место поднялось. При сбое —
автоматический откат образа и данных.

## Чего нет в локальном режиме

- Автокоммитов: на сервере платформа страхует проекты git-автосейвом, здесь
  `/workspace` — ваши настоящие репозитории, коммиты делаете вы (или агент
  по вашей просьбе).
- Удаления папок из интерфейса: удаление воркспейса в dsh не стирает каталог
  на диске.
- Регистрации, ролей, квот, админки — это серверные вещи.

## Если что-то не так

| Симптом | Что сделать |
|---|---|
| `docker недоступен` | запустите Docker Desktop / dockerd |
| `образ … нет локально` | `docker login <реестр>`, затем `agctl dev update` |
| «Добавьте ключ API» в чате | `agctl dev secrets set AGCTL_LLM_API_KEY`, `down` + `up` |
| агент не видит GitLab/Jira | `agctl dev doctor` (сеть, доступы), `secrets list` |
| мост: «мост недоступен» | `agctl dev status`; на Linux — есть ли интерфейс docker0 |
| порт занят | `addr` в `dev.yaml` (только 127.0.0.1) |
