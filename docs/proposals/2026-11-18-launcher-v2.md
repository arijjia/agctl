# Лаунчер v2 и «Возможности»: предложение на согласование

> Черновик 2026-11-18. Ничего из описанного ещё не реализовано: документ
> нужен, чтобы согласовать архитектуру до начала работы. Первая волна —
> только локальный режим (`agctl dev`), серверный догоняет следующим шагом.

## 1. Как сейчас устроены скиллы и MCP

### Скиллы

Скилл — каталог `<имя>/SKILL.md` (или файл `<имя>.md`) с описанием в
шапке. dsh собирает их из нескольких корней одновременно
(`dsh-skill-filesystem`), более ранний корень выигрывает при совпадении
имени:

| Ранг | Корень | Что это в нашем контейнере |
|---|---|---|
| 100 | `<корень проекта>/.dsh/skills` | скиллы конкретного проекта; корень проекта — ближайший каталог с `.git` |
| 200 | `<корень проекта>/.agents/skills` | то же, «межхарнесный» формат |
| … | свои каталоги из конфигурации | можно добавить любой путь |
| пользователь | `$DSH_HOME/skills` | `/home/dsh/skills` — общие для всего контейнера |
| пользователь | `~/.agents/skills` | в контейнере `HOME=/workspace`, то есть `/workspace/.agents/skills` |
| встроенные | бандлы пакетов dsh | офисные и прочие скиллы самого dsh |

Сейчас agctl умеет только проектный уровень: пакет каталога из профиля
организации копируется файлами в `<проект>/.dsh/skills/…`. Уровня «общие
скиллы на весь контейнер» в интерфейсе нет, хотя dsh его поддерживает.

### MCP

MCP — это протокол «клиент — сервер». **Клиент — сам dsh внутри
контейнера** (плагин `@deepseek-ai/dsh-mcp-client`). **Сервер** — внешняя
программа, которая отдаёт агенту инструменты; агент видит их как свои
(`mcp__<сервер>__<инструмент>`). Сервер подключается одним из двух
транспортов:

- **stdio** — dsh сам запускает процесс внутри контейнера (например
  `npx @zereight/mcp-gitlab`), общается с ним через stdin/stdout; процесс
  видит файловую систему и окружение контейнера;
- **streamable HTTP** — сервер уже работает где-то как сервис, dsh ходит к
  нему по URL. Так устроены 1С-MCP.

Область действия MCP — **не папка, а место, где сервер описан**. В dsh
есть два способа:

- **менеджер MCP профиля** (`@deepseek-ai/dsh-mcp-manager`, поле
  `config.servers` записи профиля): серверы на весь контейнер. Менеджер
  подключает, перестраивает и отключает их на лету без перезапуска dsh,
  отдаёт браузеру живой статус каждого сервера (`ctx.remote.mcpManager.watch`)
  и подставляет секреты шаблонами `${credential:REF}` из
  `.credentials.yaml`, так что ключи не лежат в конфигурации;
- **строка в составе пресета** (`.agent-presets/<id>/agent.cordis.yml`):
  сервер получают только сессии, созданные с этим пресетом. Так удобно
  делать серверы конкретного проекта.

Сейчас agctl делает только второй вариант: консоль «Возможности» пишет
пресет `agctl-ws-<проект>` с выбранными серверами из платформенного
каталога (DuckDuckGo, Context7, Tavily, GitLab, Jira, Playwright, мост к
хосту), и пользователь должен **сам выбрать этот пресет** при создании
сессии. Поддерживается только stdio.

### 1С-MCP

Пакет `1c-mcp` профиля utmn — девять купленных серверов vibecoding1c
(справка платформы, код и граф метаданных, БСП, шаблоны, синтаксис BSL,
1С:Напарник, QA, КД 2.0). Это **HTTP-серверы в docker compose на машине
разработчика**, порты 8000–8020 только на `127.0.0.1`; из контейнера они
доступны по `http://host.docker.internal:<порт>/mcp`. Им нужны лицензионные
ключи и пути к выгрузке конфигурации и платформе 1С.

Сейчас пакет ставится в проект **файлами**: compose-файл, документация,
`mcp-call.sh` и скилл с адресами. Агент вызывает серверы через скрипт и
curl, а не как родные MCP-инструменты: строк `streamable-http` agctl не
создаёт. Это главный пробел, который лаунчер v2 закрывает (раздел 4.4).

## 2. Чего хотим

- Несколько рабочих мест (контейнеров) у одного разработчика.
- При создании контейнера — выбор папки на хосте (→ `/workspace`), образа,
  набора возможностей (скиллы, MCP, инструменты), модели и ресурсов.
- Понятная библиотека возможностей: наборы для разных групп разработчиков,
  уровни «весь контейнер» и «проект», статус подключения MCP, переход к
  файлу скилла в Finder и VS Code.
- Страница моделей: все провайдеры и модели, сравнение по умности на
  разных уровнях усилий и по бенчмаркам, ключи к провайдерам.
- Все секреты — только через лаунчер, в том числе изнутри dsh.
- Бэклог рядом.
- Тот же интерфейс и в отдельной вкладке браузера, и внутри dsh в правой
  панели — без расхождений и конфликтов.

## 3. Ключевое решение: один источник правды, один интерфейс, два места показа

```
                       ┌───────────────────────────────────────────┐
                       │ agctl (Go) — единственный, кто ПИШЕТ       │
                       │  состояние: рабочие места, маунты, наборы, │
                       │  модели и ключи, секреты                   │
                       │  REST /api/v2/* + поток событий /api/events │
                       └──────────────┬────────────────────────────┘
                 читает/пишет только  │  генерирует файлы для dsh
                 через API            │  (пресеты, .credentials.yaml,
          ┌───────────────────────────┤   скиллы контейнера)
          ▼                           ▼
  Лаунчер (SPA, вкладка браузера)   DSH_HOME каждого контейнера
  /launcher — полный пульт          (dsh только читает эти файлы)
          ▲
          │ тот же React-код, режим «встроенный», без шапки,
          │ с привязкой к текущему контейнеру
  dsh: правая панель (плагин agctl-panels)
  вкладки «Возможности», «Модели», «Секреты», «Бэклог»
  = iframe на /launcher/embed/<раздел>?ws=<id>
```

Почему так:

- **Нет двух реализаций.** Интерфейс пишется один раз (React в `web/`).
  Плагин dsh — тонкая обёртка: регистрирует табы правой панели (тем же
  способом, что `model-picker` webmalex: сервисы `sidebarRightTabs` и
  слоты `sidebar.right.pane.tab`) и показывает в них встроенный лаунчер.
  Это работает без CORS и без отдельного входа: dsh у нас открыт через
  прокси agctl на том же адресе (`/chat/`), поэтому iframe `/launcher/embed`
  получает ту же cookie-сессию agctl.
- **Нет конфликтов «галочка тут, галочка там».** Писать может только agctl.
  У каждого ресурса номер ревизии; изменение отправляется с ним
  (`If-Match`), и устаревшее изменение отклоняется с понятным сообщением.
  Обе открытые копии интерфейса подписаны на `/api/events` и обновляются
  сами в течение секунды.
- **dsh не редактирует то, чем управляет agctl.** Файлы, которые agctl
  генерирует (пресеты, `.credentials.yaml`, общие скиллы контейнера),
  помечены как управляемые и перезаписываются из состояния. Ручные
  настройки dsh пользователя (свои пресеты, свои скиллы) не трогаются.

Что где показывается:

| Раздел | Лаунчер (вкладка браузера) | Внутри dsh (правая панель) |
|---|---|---|
| Рабочие места: создать, запустить, остановить, удалить, логи, ресурсы | да | только карточка текущего (статус, перезапуск) |
| Папки на хосте и маунты | да, с выбором папки | только просмотр |
| Возможности: наборы, скиллы, MCP, инструменты | вся библиотека и все контейнеры | текущий контейнер и текущий проект |
| Модели и ключи провайдеров | да | да; плюс «сделать моделью этой сессии» |
| Секреты | да | да (тот же экран, те же данные) |
| Бэклог | да | да |

Внутри dsh не будет ничего, что меняет сам контейнер так, что dsh пришлось
бы перезапускать изнутри себя (смена образа, маунтов, удаление): такие
действия ведут в лаунчер ссылкой «Открыть в лаунчере».

Плагины `workspace-console` («Возможности» в левой панели) и `cabinet`
заменяются табами правой панели; переход идёт постепенно, старые плагины
убираются, когда новые табы покрывают их функции.

## 4. Что меняется в agctl

### 4.1 Несколько рабочих мест

Сейчас у пользователя ровно один рантайм (`ensureChat(userID)`). Вводится
сущность **рабочее место**: имя, образ, маунты, набор возможностей, модель
по умолчанию, ресурсы, состояние. Рантайм привязывается к рабочему месту, а
не к пользователю; адрес чата — `/w/<имя>/chat/` (старый `/chat/` ведёт в
рабочее место по умолчанию). Данные каждого места — свой домашний каталог
dsh (`chats/u<ID>/<имя>/dsh-home`), чтобы сессии и настройки не смешивались.

> **Как сделано (2026-11-19).** В `main` пришли слоты developer'а
> (`developer-multi-containers`: `chatKey{uid, slot}`, свой том и образ на
> слот, API `/api/me/slots`). Рабочее место построено поверх них: место =
> слот, таблица `places` хранит только имя, id для адреса `/p/<id>/` и папки
> хоста; образ — в `settings` слота, как у серверного лаунчера. Одна модель
> для обоих режимов; подробности — `docs/architecture.md`, раздел 6.9.

### 4.2 Папка на хосте

В мастере создания — **выбор папки деревом каталогов** (сервер отдаёт список
подкаталогов в разрешённых корнях: домашний каталог, кроме служебных и
`$HOME` целиком; запрещено то же, что сейчас запрещает `ValidateWorkDir`).
Можно подключить несколько папок: каждая станет `/workspace/<имя>`, или одну
как `/workspace`. Кнопки «Показать в Finder» и «Открыть в VS Code» вызывают
на хосте `open -R` / `code` (только локальный режим, только пути внутри
маунтов).

### 4.3 Библиотека возможностей и наборы

Единая модель **возможности**: вид (скилл, MCP-сервер stdio или HTTP,
инструмент или скрипт, промпт, шаблон), описание, источник (профиль
организации, платформа, пользователь), требования (секреты, порты, образ).

**Наборы** — именованные списки возможностей для групп разработчиков
(«1С-разработка», «фронтенд», «аналитика»): задаются в профиле организации
(`catalog/sets/*.yaml`), пользователь может собрать свой. Набор
выбирается при создании рабочего места и меняется потом.

Два уровня установки:

- **контейнер** — скиллы в `/home/dsh/skills`, MCP в менеджере MCP профиля
  (подключаются на лету, видны всем сессиям, выбирать пресет не нужно,
  ключи — через `${credential:REF}`);
- **проект** — скиллы в `<проект>/.dsh/skills` (как сейчас), MCP в пресете
  проекта.

На экране — карточки с видом, уровнем, источником и статусом; у MCP —
состояние подключения и список инструментов (данные из `dsh-mcp-manager`);
у скилла — путь на хосте, просмотр и кнопки Finder и VS Code.

Отдельный вопрос для песочницы — убедиться, что пресеты проекта и менеджер
профиля не дают двух серверов с одним именем в одной области: менеджер такие
записи отклоняет при записи, и лаунчер должен показать это заранее.

### 4.4 MCP по HTTP

Каталог MCP получает транспорт `streamable-http` с адресом и заголовками
(менеджер MCP dsh его поддерживает).
1С-MCP из профиля utmn становятся девятью такими записями
(`http://host.docker.internal:800N/mcp`) и подключаются агенту как родные
инструменты. Лаунчер проверяет доступность порта на хосте и подсказывает,
какой профиль docker compose поднять.

### 4.5 Модели

Страница строится на тех же данных, что `model-picker` webmalex:

- живой каталог провайдеров и моделей dsh (`session/modelCatalog`);
- карта умности по уровням усилий `low…max` и бенчмаркам (Artificial
  Analysis; формат `model-map/2` из `modelctl`, со встроенной копией на
  случай, если `modelctl` нет), контекст, зрение, параметры;
- ключ к каждому провайдеру (хранится в секретах agctl и попадает в
  `.credentials.yaml` всех контейнеров), модель по умолчанию для рабочего
  места;
- внутри dsh — дополнительно «переключить модель этой сессии».

### 4.6 Секреты

Единое хранилище (локально — хранилище ОС, как сейчас). Уровни: «для всех
рабочих мест» и «для одного». Значения в интерфейс не возвращаются ни в
лаунчере, ни в dsh.

### 4.7 Бэклог

Таб с карточками `backlog/` текущего проекта (формат `gitctl backlog`, как
`backlog-board` webmalex): список, фильтры, открыть файл. Только чтение в
первой волне.

## 5. Как будем проверять

Новый лаунчер разрабатывается в ветке и запускается **отдельным экземпляром**,
не трогая текущий `~/.agctl-dev` и контейнер:

```bash
AGCTL_DEV_HOME=~/.agctl-dev-sandbox agctl dev up --addr 127.0.0.1:8931
```

Плагин правой панели проверяется в контейнере песочницы. Релиз — только
после совместной сверки.

## 6. Порядок работ

1. **Лаунчер v2, локальный режим:** рабочие места (несколько), мастер
   создания с выбором папки и набора, Finder и VS Code, модели, секреты,
   встроенный режим `/launcher/embed`.
2. **Возможности:** модель возможностей и наборов, уровень «контейнер»,
   MCP по HTTP, 1С-MCP как родные инструменты.
3. **Плагин правой панели dsh** с табами; уход от `workspace-console` и
   `cabinet`.
4. **Бэклог** и серверный режим (те же экраны, роли и квоты).

## 7. Что нужно решить

1. Папки: одна папка на рабочее место (`/workspace`) или несколько
   (`/workspace/<имя>`)? Предлагаю несколько, с одной главной.
2. Наборы возможностей: только из профиля организации или ещё и свои у
   пользователя? Предлагаю оба, свои — поверх профильных.
3. Отдельный домашний каталог dsh на каждое рабочее место (сессии не
   смешиваются) или общий? Предлагаю отдельный.
4. Внутри dsh — один таб «agctl» с разделами или несколько табов
   («Возможности», «Модели», «Секреты», «Бэклог»)? Предлагаю несколько:
   так в правой панели меньше вложенности.
