# agctl

**Платформа агентских рабочих мест.** Пользователь работает в браузере с
чатом агента DeepSeek Harness (`dsh`), а агент исполняется в отдельном
контейнере с инструментами разработчика, каталогом проектов и доступами к
модели, GitLab и Jira. agctl создаёт и усыпляет эти контейнеры,
аутентифицирует пользователей, проксирует их браузер к агенту, готовит
настройки агента и подключает профиль организации (бренд, модели, образы).

Платформа работает в трёх режимах, которые собираются из одного ядра в
отдельные бинари:

| Режим | Бинарь | Для кого | Где работает агент |
|---|---|---|---|
| [Локальный](#локальный-режим) | `agctl` | один разработчик на своей машине | контейнер в локальном Docker; `/workspace` — папка проектов машины |
| [Серверный](#серверный-режим) | `agctl-server` | организация, много пользователей и ролей | контейнер на пользователя в Docker хоста |
| [Кластерный](#кластерный-режим) | `agctl-server --runtime k8s\|ax` | организация без отдельного Docker-хоста | под Kubernetes или актор Google AX / Agent Substrate на пользователя |

Третий бинарь, `agctl-guest`, живёт внутри образа рабочего места
(`/usr/local/bin/agctl`). Он собирается в двух вариантах из одного кода,
каждый под свой режим и своё семейство образов: локальный вариант (только
мост к хосту) — в образах `agctl-dsh*`; серверный (`-tags server`: раннер
AX и init-контейнер Kubernetes) — в образах `agctl-dsh-server*`.
Пользователь его не запускает.

Как система устроена внутри — процессы, сети и порты, данные и секреты,
разбор кодовой базы по режимам — описано в
[docs/architecture.md](docs/architecture.md).

## Локальный режим

`agctl dev` поднимает на машине разработчика платформу для одного
человека: в браузере открывается чат с агентом, агент работает в
контейнере на локальном Docker, видит только выбранную папку проектов и
ходит в GitLab, Jira и модель с доступами из хранилища ОС. Клонировать
репозиторий не нужно: достаточно бинаря `agctl` и Docker.

### Что нужно

- **Docker**: Docker Desktop (macOS; Windows 10/11 с бэкендом WSL 2), Docker
  Engine (Linux), либо Colima / Rancher Desktop / Podman Desktop.
  `docker version` должен отвечать без ошибок.
- **Бинарь `agctl`** под вашу ОС — ниже два способа его получить.
- 8 ГБ ОЗУ и около 20 ГБ диска: образ рабочего места с инструментами —
  около 4 ГБ, с браузерами — около 5,5 ГБ.
- Ключ модели (OpenAI-совместимый провайдер: LiteLLM организации или
  публичный) — выдаёт команда платформы. Свою подписку можно подключить
  в настройках dsh внутри чата: личный провайдер перекрывает платформенный.

### Установка из релиза

Релизы собираются goreleaser по тегу `v*` и публикуются на странице
[Releases](https://github.com/arijjia/agctl/releases): архивы
`agctl_<ос>_<архитектура>`, `agctl-guest_linux_<архитектура>` (локальный
guest), `agctl-guest-server_linux_<архитектура>` (серверный guest),
`agctl-server_<ос>_<архитектура>` и `checksums.txt`. Если список релизов
пуст, тег ещё не выпускался: соберите из исходников (раздел
[Сборка из исходников](#сборка-из-исходников)) или возьмите сборку у
команды платформы.

macOS и Linux:

```bash
curl -fsSL https://raw.githubusercontent.com/arijjia/agctl/main/bin/install.sh | sh
```

Windows 10 / 11, PowerShell:

```powershell
irm https://raw.githubusercontent.com/arijjia/agctl/main/bin/install.ps1 | iex
```

Скрипт ([bin/install.sh](bin/install.sh), [bin/install.ps1](bin/install.ps1)):

1. определяет ОС и архитектуру;
2. скачивает архив последнего релиза и `checksums.txt` (через `gh`, если он
   установлен и авторизован, иначе напрямую) и сверяет SHA-256;
3. кладёт `agctl` в `~/.agctl/bin` (Windows: `%USERPROFILE%\.agctl\bin`) и
   снимает карантин macOS или отметку «скачано из интернета» на Windows;
4. кладёт `agctl-guest-linux-<arch>` (локальный guest) и
   `agctl-guest-server-linux-<arch>` (серверный guest) в `~/.agctl/bin/guest`:
   они нужны, чтобы собрать образ рабочего места на этой машине, если
   реестр образов недоступен — свой вариант под локальный (`agctl-dsh*`) и
   серверный (`agctl-dsh-server*`) режимы;
5. на Windows добавляет `bin` в `PATH` пользователя, на macOS и Linux
   подсказывает строку для профиля оболочки
   (`export PATH="$HOME/.agctl/bin:$PATH"`), если каталога в `PATH` нет, и
   печатает `agctl version`.

Всё, что agctl держит на машине, лежит под одним корнем `~/.agctl`
(раздел [«Где что лежит»](#где-что-лежит)). Переменные окружения скрипта:
`AGCTL_VERSION=v0.1.0` (конкретный тег), `AGCTL_ROOT` (другой корень),
`AGCTL_NO_LINUX=1` (без `agctl-guest`, если образы берутся из реестра),
`AGCTL_RELEASE_DIR` (папка с уже скачанными архивами), `AGCTL_WORKDIR` и
`AGCTL_NO_INIT=1` (для комплекта организации, см. ниже).

**Комплект организации.** Организация может публиковать свой релиз в
приватном репозитории профиля `<org>/agctl-profile-<id>`: архив с `agctl`,
`agctl-guest-linux-<arch>`, `agctl-guest-server-linux-<arch>` и профилем
организации. Доступ проверяется
учётной записью GitHub: администратор добавляет разработчика в этот
репозиторий с правом чтения, а разработчик один раз ставит GitHub CLI
(`brew install gh`, `winget install GitHub.cli` или пакет дистрибутива) и
входит командой `gh auth login`. Затем:

```bash
curl -fsSL https://raw.githubusercontent.com/arijjia/agctl/main/bin/install.sh | AGCTL_REPO=<org>/agctl-profile-<id> sh
```

```powershell
$env:AGCTL_REPO = '<org>/agctl-profile-<id>'; irm https://raw.githubusercontent.com/arijjia/agctl/main/bin/install.ps1 | iex
```

Профиль кладётся в `~/.agctl/profiles/<id>`, и скрипт сразу создаёт для
него **свой дом** `~/.agctl/homes/<id>` командой
`agctl dev --home <id> init --profile <id> --yes` — дом по умолчанию и дома
других организаций не затрагиваются. Запуск: `agctl dev --home <id> up`
(если дом на машине один, `--home` можно не писать). Отключить авто-init
можно переменной `AGCTL_NO_INIT=1`, папку проектов задаёт `AGCTL_WORKDIR`.
Повторный запуск
обновляет бинари и профиль на месте. Те же шаги вручную, по командам для
каждой ОС, — в [docs/install-manual.md](docs/install-manual.md). Живьём на
Windows локальный режим ещё не прогонялся, поэтому первый запуск там стоит
делать вместе с командой платформы.

### Запуск

Настроить профиль организации и папку проектов (пишет
`~/.agctl/homes/<id>/config.yaml`):

```bash
agctl dev init
```

Поднять платформу в фоне и открыть браузер со ссылкой входа:

```bash
agctl dev up
```

`up` проверяет Docker и свободный порт, запускает платформу в фоне на
`http://127.0.0.1:8930` и открывает браузер с одноразовой ссылкой входа.
Если на машине ещё нет ни одного дома, первый `agctl dev up` настраивает
дом сам (как `agctl dev init --yes`): папка проектов — аргумент `up` или
`~/src`, остальное — в лаунчере.
Пароля и регистрации нет: вы единственный пользователь.

После входа открывается **лаунчер** с четырьмя вкладками:

- **Рабочие места** — каждое место — отдельный контейнер со своим образом,
  своими папками и своим домашним каталогом dsh (сессии, скиллы,
  настройки). **Основное** место — папка проектов из `config.yaml` (станет
  `/workspace`) и образ из профиля, его чат — `/chat/`. **Дополнительные**
  места (до семи) создаются мастером: имя, папки (дерево или системный
  диалог выбора; одна папка → `/workspace`, несколько →
  `/workspace/<имя>`) и образ; их чат — `/p/<id>/`. Образы — из каталога
  профиля (базовый, минимальный, `web` с Playwright и Chromium, вкус
  профиля организации) с отметкой «есть на машине» и версией dsh: «Запустить» скачивает недостающий
  образ из реестра или собирает его на месте (10–20 минут, прогресс на
  странице). У карточки места — «Перезапустить», «Остановить», логи,
  «Показать в Finder» и «Открыть в VS Code». Удаление места архивирует его
  данные dsh, папки на диске не трогаются.
- **Образы** — каталог образов профиля: есть ли на машине, вид (полный,
  минимальный, web), версия dsh, сборка guest, дата, размер и какие места
  его используют. «Как собирается» показывает ступени сборки (базовый →
  вкус → надстройка профиля): откуда образ скачивается, Dockerfile каждой
  ступени с подсветкой, аргументы, файлы контекста сборки — откуда каждый
  (встроен в бинарь agctl, скелет dsh-home, guest-бинарь на диске, файл
  профиля) и какого размера; файл открывается текстом с подсветкой, каталог —
  списком файлов. Ниже — что качается из сети (базовые образы, пакеты apt
  и npm, загрузки). Действия: «Скачать или собрать» недостающий; «Скачать
  из реестра» — свежий образ из реестра образов, в том числе для
  работающего места (новая версия применится при его перезапуске);
  «Пересобрать» — собрать на этой машине, без реестра (готовые нижние
  ступени и слои — из кэша Docker); «Удалить». Образ работающего места не
  пересобирается и не удаляется.
- **Пресеты** — наборы MCP-серверов и скиллов, отмеченные галочками, и
  места, к которым они применяются. agctl кладёт пресет в домашний каталог
  dsh мест, а в dsh он выбирается при создании сессии.
- **Модели** — провайдеры и модели платформы из профиля и статус ключа
  каждого. Профиль может разрешить агенту запускать сабагентов на быстрых
  моделях (`llm.subagent_models` — «модель» или «алиас/модель» через
  запятую): основной диалог остаётся на большой модели, мелкие задачи
  уходят быстрой; в dsh это настройка выбора модели сабагента. Новый шлюз
  моделей (корпоративный LiteLLM, vLLM) проверяет `agctl dev llm-check`:
  отвечает ли каждая модель и вызывает ли инструменты — без этого агент на
  ней работать не сможет (`--insecure` — отличить сертификат шлюза от
  модели).
- **Доступы** — ключ модели, адрес и токен GitLab, адрес, логин и токен
  Jira, свои переменные. Значения уходят в хранилище ОС (Keychain, Диспетчер
  учётных данных, Secret Service) и обратно на страницу не возвращаются.
  Доступы общие для всех мест. Пока ключа модели нет, рядом с вкладкой
  стоит ⚠. Пустые доступы `agctl dev up` берёт из переменных окружения
  машины (`AGCTL_LLM_API_KEY`, `JIRA_API_TOKEN`, `JIRA_USERNAME`,
  `CONFLUENCE_PERSONAL_TOKEN`, `GITLAB_TOKEN`, ключи провайдеров профиля и
  то, что профиль назвал в `env_from`): заданное в лаунчере окружение не
  перезаписывает, удалённое снова берётся из окружения; выключается
  `env_import: false` в `config.yaml`. Список — `agctl dev secrets list`.

Если образ основного места на машине и ключ задан, оно стартует сразу при
входе. Переключатель светлой и тёмной темы — в шапке лаунчера.

Папки мест — это ваши настоящие репозитории: автокоммитов нет,
удалить папку из интерфейса нельзя, слева в чате видны только её подпапки.
`agctl dev up ~/src/проект` поднимает платформу с другой папкой основного
места. Профиль организации подключается через `agctl dev init --profile
<id>` (профиль лежит в `~/.agctl/profiles/<id>`); без него работает
встроенный нейтральный профиль `agctl`. Профиль может наследовать другой
(`extends`): вариант организации — например контур разработки с её шлюзом
моделей — держит только отличия и может лежать подкаталогом в репозитории
базового профиля (`profiles/org/dev` с `id: org-dev` находится по
`--profile org-dev`). Адреса Jira, Confluence, GitLab организации профиль
задаёт в `env` — у разработчика они уже заполнены.

### Где что лежит

Локальный режим держит всё под одним корнем — `~/.agctl` (Windows:
`%USERPROFILE%\.agctl`; другой корень — переменная `AGCTL_ROOT`):

```
~/.agctl/
  bin/agctl, bin/agctl-server           бинари (этот каталог — в PATH)
  bin/guest/agctl-guest[-server]-linux-<arch>   guest для сборки образа
  profiles/<id>/                        профиль организации — один экземпляр:
                                        распакованный комплект, клон или ссылка на репозиторий
  homes/<id>/                           дом: по одному на установку
    config.yaml                         настройки дома; у каждого поля комментарий
    data/                               база настроек, сессии браузера, данные dsh
    logs/serve.log, logs/bridge.log     журналы процесса и моста
    run/state.json                      фоновый процесс: pid, адрес, токены
    backups/                            три последних резервных копии данных dsh
```

`agctl dev paths` печатает то же самое для вашей машины с настоящими
путями: корень, бинари, guest, профиль (путь и чем он разрешён), дом и
каждый его файл с назначением, папку проектов, адрес интерфейса и порт
моста, имена контейнеров, образ, docker-сеть egress, bind-маунты
хост → контейнер и место хранения секретов. `agctl dev paths --json` —
машинный вывод.

Правила:

- **Дом** выбирается так: `agctl dev --home <id> …` > переменная
  `AGCTL_HOME_ID` > единственный существующий дом > `agctl`. Флаг `--home`
  действует на любую подкоманду. `agctl dev init --profile <id>` на чистой
  машине создаёт дом с id профиля.
- **Профиль** ищется одним способом и для команд, и для фонового процесса:
  `profile_dir` из `config.yaml` > `~/.agctl/profiles/<id>` > встроенный в
  бинарь. Текущий каталог на поиск не влияет.
- **Из профиля в дом ничего не копируется.** Образ по умолчанию и
  инструменты моста профиля (`local/bridge-tools.yaml`) читаются из профиля
  на каждом старте; в `config.yaml` — только ваш явный выбор образа и ваши
  личные инструменты моста.
- **Секреты** хранилища ОС лежат в отдельном сервисе на каждый дом —
  `agctl:<id дома>`: ключи разных организаций не смешиваются.
- Серверный `~/.config/agctl/config.yaml` и переменные серверного запуска
  (`AGCTL_LLM_*`, `AGCTL_EGRESS_*`, `AGCTL_PUBLIC_URL`, `AGCTL_CORS_ORIGINS`,
  в том числе из `.env` репозитория) на локальный режим не влияют: фоновый
  процесс снимает их при старте.

**Несколько установок на одной машине** (например, свой нейтральный agctl
и профиль организации рядом) — это несколько домов; у каждого свой порт,
контейнеры, данные и секреты:

```bash
agctl dev --home <id> init --profile <id> --workdir ~/src/<id> --addr 127.0.0.1:8931 --yes
agctl dev --home <id> up
```

**Переход со старой раскладки.** Раньше дом лежал в `~/.agctl-dev` (или
`~/.agctl-dev-<id>`), бинарь — в `~/.local/bin`, guest — в
`~/.local/lib/agctl`, профиль комплекта — в `~/.local/share/agctl/profiles`.
`agctl dev migrate` показывает план переноса домов в `~/.agctl/homes/<id>`
(id дома = id профиля, `dev.yaml` становится `config.yaml`), `agctl dev
migrate --apply` выполняет его; перед переносом остановите платформу
(`agctl dev down`). Имена Docker-контейнеров содержат хеш пути `data/`,
поэтому после переноса рабочие места создаются заново под новыми именами
(данные лежат на маунтах и сохраняются), а команду удаления старых
контейнеров `migrate` печатает. Секреты прежнего общего сервиса `agctl-dev`
копируются в сервис дома и продолжают читаться как запасной источник.
Старые бинари в `~/.local/bin` и `~/.local/lib/agctl` удалите сами, чтобы
в `PATH` не остался прежний `agctl`.

### Команды

| Команда | Что делает |
|---|---|
| `agctl dev [--home ID] <команда>` | выбрать дом для любой команды ниже |
| `agctl dev init [--profile ID \| --profile-dir DIR] [--flavor web\|<вкус профиля>] [--image REF] [--workdir DIR] [--addr 127.0.0.1:PORT] [--runtime docker\|sbx] [--host-paths=false] [--yes] [--cli]` | настроить дом: профиль и папку проектов; образ и доступы — в лаунчере (`--cli` — мастером в терминале); новый дом — с путями как на хосте |
| `agctl dev up [DIR] [--no-open] [--foreground] [--runtime docker\|sbx]` | поднять платформу в фоне и открыть браузер; после обновления бинаря сам перезапускает фоновый процесс старой сборки |
| `agctl dev down` | остановить платформу и контейнер; сессии и настройки сохраняются |
| `agctl dev status` | адрес, образ, папка, сборка, состояние рабочего места и моста |
| `agctl dev paths [--json]` | где что лежит: корень, бинари, профиль, дом и его файлы, порты, контейнеры, образ, сеть egress, маунты, секреты |
| `agctl dev open` | новая ссылка входа в браузере |
| `agctl dev logs [-f]` | журнал фонового процесса |
| `agctl dev secrets list \| set ИМЯ [--stdin] [--plain] \| rm ИМЯ` | доступы: список без значений, задать (ввод скрыт; `--plain` — несекретное значение в `config.yaml`), удалить |
| `agctl dev bridge list \| pending \| approve ID \| deny ID \| log` | мост к хосту: белый список, ожидающие подтверждения вызовы, решение, журнал |
| `agctl dev update [--image REF]` | обновить образ: скачать из реестра образов (не вышло — локальный образ или сборка на машине), сделать резервную копию данных dsh, перезапустить, проверить, при сбое откатить |
| `agctl dev rollback [--restore-data]` | вернуть предыдущий образ и при необходимости данные dsh |
| `agctl dev doctor` | самодиагностика: Docker, рантайм (sbx: установлен, вход, виртуализация), образ, профиль, папка, доступы, сеть до модели, GitLab и Jira, мост |
| `agctl dev migrate [--apply]` | перенести прежние дома `~/.agctl-dev[-<id>]` в `~/.agctl/homes/<id>`; без `--apply` — только план |
| `agctl version`, `agctl completion fish`, `agctl help` | версия и сборка, автодополнение для fish, справка |

Внутри контейнера (бинарь образа `agctl-guest`): `agctl bridge list | call
ИНСТРУМЕНТ k=v … | mcp` — вызвать команду хоста из белого списка; `mcp`
запускает MCP-сервер «Мост к хосту».

Переменные окружения: `AGCTL_ROOT` — корень (по умолчанию `~/.agctl`);
`AGCTL_HOME_ID` — id дома (то же, что `--home`); `AGCTL_DEV_HOME` —
абсолютный путь дома вне корня (для тестов и e2e);
`AGCTL_DEV_SECRETS=file` — хранить секреты в зашифрованном файле
`secrets.enc` дома вместо хранилища ОС; `NO_COLOR` — справка без цвета.

### Рабочие места: dsh-home, клон, пути как на хосте

- **Пути как на хосте.** Папки проектов видны в контейнере ещё и по своим
  путям на этой машине (`/Users/…/src`, `/home/user/src`), процесс агента,
  `HOME` и воркспейс dsh по умолчанию — там же: пути в сессиях агента
  открываются во внешнем редакторе, предложенные им команды выполняются на
  хосте как есть. `/workspace` остаётся (прежние сессии и скиллы). Новый
  дом включает режим сам (`host_paths: true` в `config.yaml`, кроме
  Windows), прежний — переключателем в лаунчере («Рабочие места») или
  `agctl dev init --host-paths`. Только рантайм docker; системные каталоги
  образа (`/usr`, `/etc`, `/workspace`, …) по своему пути не монтируются.
- **Своя папка dsh-home.** В мастере места можно выбрать «своя папка» —
  например `~/src/ag_dsh`: dsh-home (скиллы, пресеты, плагины, настройки,
  сессии) живёт там, а папка становится git-репозиторием конфигурации
  агента: `.gitignore` без секретов, сессий, кэшей и пресетов лаунчера,
  первый коммит — после первого запуска. Карточка места показывает
  состояние git и подсказку залить репозиторий на свой Git; тот же
  репозиторий подключается к месту на другой машине.
- **Клонировать.** Новое место с теми же папками и образом и копией
  dsh-home (сессии, скиллы, настройки, пресеты): пробовать новую версию
  образа или плагины без риска для исходного места; заодно ручной бэкап.
  На macOS копия — клон APFS (место на диске не тратится), на Linux —
  reflink, иначе обычная копия. Работающее исходное место на время копии
  останавливается и запускается снова.

### Образы рабочего места и версии dsh

Каталог образов лаунчера задаёт профиль (`images.dev`); у каждого образа
лаунчер показывает, что внутри: версию dsh, сборку guest agctl, дату и
размер, — и предупреждает, если образ старее платформы (собран до нужной
этой сборке возможности guest или до меток версий). То же в терминале:

```bash
make img_list
```

| Образ | Что внутри |
|---|---|
| `agctl-dsh:<тег>` | dsh, git, glab, jira-cli, uv, kubectl, клиенты БД, офис для превью, MCP-кэш |
| `agctl-dsh-min:<тег>` | только node, git, dsh и guest — «чистый» dsh |
| `agctl-dsh-web:<тег>` | базовый + Playwright и Chromium для агента |

Тег вида `0.2.3-alpha.2` или `0.2.2-rc.5` — **версия dsh**: такой образ
собирается на этой версии (`make img_dsh DSH=0.2.3-alpha.2`, либо лаунчер
сам при первом запуске места). Апгрейд dsh у места — выбрать образ с новой
версией и перезапустить; откат — выбрать прежний. Пробовать новую версию
удобно на клоне места. Слои образа — от редких изменений к частым (тулчейн
→ офис и CLI → MCP-кэш → dsh → файлы agctl), поэтому новая версия dsh —
это пересборка и `docker pull` только верхних слоёв (около 1,8 ГБ из 4,4;
сборка — минуты, а не полный прогон apt).

**Откуда берётся образ.** Готовые образы публикует воркфлоу `images`
(вручную или тегом `v*`) в `ghcr.io/arijjia/agctl-dsh` и `agctl-dsh-min`
для linux/amd64 и arm64. Образ с локальным именем (`agctl-dsh:0.2.2`,
`agctl-dsh-web:0.2.2`, надстройка профиля) agctl скачивает из реестра
образов — `images.registry` профиля, по умолчанию `ghcr.io/arijjia`:
`docker pull ghcr.io/arijjia/agctl-dsh:0.2.2` и тег `agctl-dsh:0.2.2`.
Если такого образа в реестре нет (вкусов `web` и надстроек профилей в
`ghcr.io/arijjia` нет) или реестр недоступен, в журнале появляется строка —
откуда тянул и почему не вышло, — и недостающее собирается на машине;
нижние ступени сначала тоже берутся из реестра, поэтому надстройка профиля
поверх скачанного базового образа собирается за минуты.
`images.registry: none` выключает реестр: образы только собираются. Так
работают запуск места в лаунчере, `agctl dev update` и
`agctl dev init --cli`, а в разделе «Образы» есть явные «Скачать из
реестра» и «Пересобрать» (на этой машине, без реестра). Образы с реестром
в имени (`ghcr.io/org/agctl-dsh:0.2.2` в `images.dev`) тянутся как есть;
если реестр ответил «нет такого», лаунчер соберёт образ на месте и даст ему
то же имя.

**Сборка без исходников.** Всё, из чего собирается образ, есть в
установленном agctl: Dockerfile ступеней, entrypoint, утилиты образа и
скелет dsh-home встроены в бинарь `agctl`, а linux-сборки guest
(`agctl-guest-linux-<arch>`) установщик `install.sh` кладёт в
`~/.agctl/bin/guest`. Поэтому пересборка работает на любой машине с
установленным agctl, в том числе без исходников; «Как собирается»
показывает каждый файл контекста и откуда он взят.

### Рантайм рабочего места: docker или sbx

По умолчанию рабочее место — контейнер в Docker. `agctl dev up --runtime sbx`
(или `agctl dev init --runtime sbx`, поле `runtime` в `dev.yaml`, лаунчер)
переключает его на [Docker Sandboxes](https://docs.docker.com/ai/sandboxes/):
microVM со своим ядром, исходящая сеть запрещена по умолчанию, ключ модели
остаётся на хосте. Нужны установленный `sbx` и вход `sbx login`;
`agctl dev doctor` покажет, готов ли он. Вернуться — `--runtime docker`,
данные при переключении сохраняются. Рантайм sbx пока не проверен на живой
установке — отличия и ограничения описаны в
[архитектуре, раздел 6.10](docs/architecture.md#610-рантаймы-рабочего-места-docker-и-sbx).

### Ограничение исходящего трафика

`egress_allowlist: true` в `config.yaml` дома сажает рабочее место на выделенную
сеть: наружу доступны только DNS, ваша машина (мост, LiteLLM на хосте),
провайдеры модели, `egress.allow` профиля и список `egress_allow` в
`config.yaml` (хосты, IPv4 или CIDR). Применяется после `agctl dev down` и
`agctl dev up`.

### Мост к хосту

Агент работает в Linux-контейнере, а часть программ есть только на вашей
машине (например, проприетарная IDE или CLI организации на Windows). Мост даёт агенту **только**
команды из белого списка: инструменты организации из
`local/bridge-tools.yaml` профиля (читаются на каждом старте) плюс ваши
личные из `bridge.tools` в `config.yaml` дома; личный инструмент с тем же
именем заменяет профильный. Весь действующий список с источником каждого
инструмента — `agctl dev bridge list`:

- команда запускается без оболочки, значение аргумента целиком уходит в
  один элемент argv;
- значения аргументов проверяются (без управляющих символов и ведущего
  `-`, либо по своему регулярному выражению `pattern`);
- инструменты с `confirm: true` ждут вашего `agctl dev bridge approve ID`;
- каждый вызов пишется в журнал `logs/bridge.log` дома.

### Если что-то не так

| Симптом | Что сделать |
|---|---|
| `неизвестная команда "dev"` | в `PATH` старый бинарь: `agctl version`, затем `make install` или свежий релиз |
| `docker недоступен` | запустите Docker Desktop или dockerd |
| `образ … нет локально` | «Скачать из реестра» в разделе «Образы» или `agctl dev update`, либо «Запустить» в лаунчере соберёт образ на месте |
| «Добавьте ключ API» в чате | вкладка «Доступы» или `agctl dev secrets set AGCTL_LLM_API_KEY` |
| `адрес 127.0.0.1:8930 занят` | `agctl dev down`; порт меняется ключом `addr` в `config.yaml` дома |
| `локальный режим не настроен`, хотя дом есть | домов несколько — выберите: `agctl dev --home <id> …`; список и пути — `agctl dev paths` |
| непонятно, откуда взялся профиль, образ или порт | `agctl dev paths` |
| после обновления браузер просит войти заново | `agctl dev open` (сессии браузера теперь хранятся в файле, старая cookie недействительна) |
| «не удаётся проверить разработчика» (macOS) | `xattr -d com.apple.quarantine` на бинаре |
| что-то ещё | `agctl dev doctor`, `agctl dev logs -f`, `agctl version` |

## Серверный режим

`agctl-server serve` — платформа для организации: много пользователей,
регистрация и вход по паролю, роли, админ-панель, контейнер рабочего места
на каждого пользователя в Docker хоста, SSH в контейнер для разработчиков.

### Что нужно

- Linux-хост (или macOS для пробного запуска) с Docker Engine и доступом
  процесса к сокету Docker.
- Бинарь `agctl-server` (архив `agctl-server_<ос>_<архитектура>` из релиза
  или `make go_build`) и образ рабочего места `agctl-dsh-server`
  (собирается `make img_build_server` или скачивается из реестра
  организации; если его нет, сервер соберёт базовый образ сам — для этого
  рядом с бинарём или в `./dist` должен лежать `agctl-guest-server-linux-<arch>`).
- Обратный прокси с TLS перед сервером (nginx, Caddy, ingress) и ключ
  модели.

### Запуск

```bash
AGCTL_LLM_API_KEY=… agctl-server serve --profile <id> --secure-cookies
```

Сервер слушает `127.0.0.1:8929` (меняет `--addr`), хранит данные в
`~/.agctl` (меняет `--home` или `AGCTL_HOME`) и встраивает интерфейс в сам
бинарь. Первый зарегистрированный пользователь становится администратором,
остальные — пользователями; роль developer выдаётся по заявке, которую
одобряет администратор. Ключ модели после первого запуска хранится
зашифрованным в базе, поэтому переменную окружения можно убрать.

Основные флаги `serve`:

| Флаг | Значение по умолчанию | Назначение |
|---|---|---|
| `--home` | `~/.agctl` | дом данных: SQLite, мастер-ключ, данные пользователей |
| `--addr` | `127.0.0.1:8929` | адрес интерфейса и API |
| `--profile`, `--profile-dir` | `agctl` | профиль организации по имени или каталогом |
| `--image` | `agctl-dsh-server:0.2.2` | серверный образ рабочего места (guest: ax-runner, init-chat-home); надстройка профиля — `agctl-dsh-server-<профиль>` |
| `--dev-images` | `images.dev` профиля | каталог образов в лаунчере разработчика |
| `--dev-env` | пусто | имена переменных окружения хоста, которые получает контейнер разработчика (например токены GitLab и Jira из `.env`) |
| `--llm-base-url`, `--llm-model`, `--llm-models`, `--llm-api-key` | из профиля | провайдер модели по умолчанию (ключ лучше передавать переменной `AGCTL_LLM_API_KEY`) |
| `--chat-ttl-min` | 60 | минуты простоя до усыпления контейнера |
| `--mem-gb`, `--cpus` | 2, 2 | лимиты контейнера |
| `--docker-runtime` | пусто (runc) | OCI-рантайм Docker-бэкенда: `runsc` (gVisor) или `kata` — изоляция ядра; должен быть зарегистрирован в dockerd |
| `--docker-pids-limit` | 4096 | лимит процессов контейнера |
| `--docker-harden` | включено | урезанные capabilities и `no-new-privileges` для контейнеров; `=0` — аварийный откат |
| `--egress-allowlist` | выключен | контейнеры на выделенной сети: наружу только DNS, хост, провайдеры модели и белый список |
| `--egress-allow` | `egress.allow` профиля | дополнительные хосты, IPv4 или CIDR через запятую (GitLab, Jira, реестр) для `--egress-allowlist` |
| `--secure-cookies` | выключен | cookie с флагом Secure (когда TLS завершается на прокси) |
| `--register-per-min` | 30 | ограничение регистраций с одного IP (0 — без ограничения) |
| `--cors-origin` | пусто | точный список источников для кросс-доменного `/api` |
| `--public-url` | вычисляется | адрес шлюза для песочниц AX |
| `--runtime` | `docker` | бэкенд рабочих мест: `docker`, `k8s`, `ax` (раздел ниже) |

Те же значения можно задать переменными `AGCTL_*` или файлом
`~/.config/agctl/config.yaml` (`agctl-server config` показывает
эффективные значения); секреты передаются только через окружение.

### Команды

| Команда | Что делает |
|---|---|
| `agctl-server serve [флаги]` | поднять платформу |
| `agctl-server migrate [--home DIR]` | применить миграции SQLite вручную |
| `agctl-server seed-demo-users [--home DIR]` | добавить тестовые учётные записи user, developer, admin (после первого настоящего администратора) |
| `agctl-server connect --port P [--host H] [--user U] [--identity KEY] [--print]` | SSH в свой контейнер (роль developer); порт берётся в Кабинете |
| `agctl-server sync create --name N --local DIR --port P \| list \| pause \| resume \| flush \| terminate` | синхронизация локальной папки с `/workspace` контейнера через Mutagen |
| `agctl-server config` | показать эффективный `config.yaml` |
| `agctl-server version`, `completion fish`, `help` | версия, автодополнение, справка |

SSH-порт контейнера разработчика публикуется только на loopback хоста,
поэтому снаружи к нему подключаются через SSH-туннель или VPN до хоста.

### Запуск из исходников на одной машине

```bash
cp .env.example .env    # вписать AGCTL_LLM_API_KEY и при необходимости другие ключи
make up PROFILE=<id>
```

`make up` собирает интерфейс, бинари и образ и поднимает
`agctl-server serve` в фоне на `127.0.0.1:8929`. Рядом: `make corp` (то же
с корпоративным LiteLLM), `make demo` (изолированный стенд в `/tmp` на
порту 8928), `make demo-users`,
`make stop`, `make down`, `make logs`, `make status`.

## Кластерный режим

Тот же `agctl-server` в кластере Kubernetes. Рабочее место каждого
пользователя — отдельный под (`--runtime k8s`: Pod, Service,
NetworkPolicy, Secret, данные на общем RWX-томе или PVC) или актор Agent
Substrate под Google AX (`--runtime ax`: задача AX в песочнице gVisor или
microVM, данные на томе актора, ключ модели можно подставлять на
egress-шлюзе Substrate, не передавая его в песочницу).

```bash
make img_serve_build img_build                   # образы шлюза agctl-serve и рабочих мест (локальные + серверные)
make img_push REGISTRY=registry.example.com/agctl
make k8s_secret                                  # Secret agctl-llm из .env
make k8s_profile PROFILE=<id>                    # профиль организации в ConfigMap
make k8s_apply K8S_OVERLAY=base                  # base | overlays/kind | overlays/ax
make k8s_status
```

Манифесты лежат в `deploy/k8s` (kustomize: base и overlays `kind`, `ax`) и
`deploy/ax` (пул воркеров AX). Ingress с TLS к Service `agctl` добавляет
оператор кластера. Настройки бэкендов — флаги `--k8s-*` и `--ax-*` или
переменные `AGCTL_K8S_*`, `AGCTL_AX_*` в Deployment. Исходящий трафик
подов пользователей можно ограничить провайдерами модели флагом
`--k8s-egress-policy`. `make k8s_e2e_kind` прогоняет смоук-тест в
одноразовом kind-кластере. Две и более реплики шлюза (overlay
`deploy/k8s/overlays/ha`, лидер через Lease, PostgreSQL) **сейчас не
работают**: код есть, но флаги `--ha-leader-lease` и `--store-dsn`
потерялись при переносе `serve` в `internal/cli` (раздел 10.4
архитектуры) — держите одну реплику. Устройство обоих
бэкендов, сети и известные ограничения — в разделе 5 и 10.4
[docs/architecture.md](docs/architecture.md). Живьём в кластере
организации эти бэкенды ещё не проверялись.

## Сборка из исходников

Нужны **Go 1.27+**, **Node 22+** (сборка интерфейса) и Docker.

```bash
git clone https://github.com/arijjia/agctl && cd agctl
make install
```

`make install` собирает интерфейс и бинари и ставит `agctl` и
`agctl-server` в `~/.agctl/bin`, оба варианта guest —
`agctl-guest-linux-<arch>` и `agctl-guest-server-linux-<arch>` — в
`~/.agctl/bin/guest` и автодополнение fish (`agctl.fish`,
`agctl-server.fish`). `AGCTL_ROOT=…` меняет корень; `~/.agctl/bin` должен
быть в `PATH`. Повторяйте после
каждого `git pull`: старый бинарь в `PATH` — частая причина ошибки
«неизвестная команда».

Другие цели (полный список — `make help`):

- `make go_build` — `dist/agctl` и `dist/agctl-server` (Node не нужен:
  `web/dist` хранится в репозитории); `make go_linux` — `agctl-guest`
  локального варианта (bridge); `make go_linux_server` — серверного
  (ax-runner, init-chat-home);
- `make go_test_all`, `make go_vet_all` — проверки в обоих вариантах guest;
- `make release_local` — все бинари для darwin, linux и windows, arm64 и
  amd64, в `dist/`;
- `make img_build [PROFILE=<id>]` — образы рабочего места: локальные
  `agctl-dsh(-nossh)` + вкус web и серверные `agctl-dsh-server(-nossh)`;
  `make img_build_server` — только серверные;
- `make uninstall` — убрать то, что поставил `install`.

### Локальный режим из исходников: по дому на профиль

Для разработки agctl и отладки профилей организаций локальный режим
поднимается целями `make local_*` ([bin/local.sh](bin/local.sh)): бинарь
собирается из текущего checkout'а, а не скачивается из релиза, и у каждого
профиля — свой дом и порт, все установки могут работать одновременно.

```bash
make local_up                        # свой agctl: профиль agctl, дом ~/.agctl/homes/agctl, порт 8930
make local_up PROFILE=<id>           # профиль из ../agctl-profile-<id>: дом ~/.agctl/homes/<id>, свой порт
make local_paths PROFILE=<id>        # где что лежит у этого дома (agctl dev paths)
make local_list                      # все дома на машине: профиль, адрес, состояние
make local_img PROFILE=<id>          # пересобрать образы с надстройкой профиля и перевести место на них
make local_down|local_status|local_logs|local_open|local_doctor PROFILE=<id>
```

- `local_up` — `make install`, затем `agctl dev init` (профиль-сиблинг,
  порт, при первом запуске папка `LOCAL_WORKDIR`, по умолчанию `~/src`) и
  `agctl dev up`; запущенный процесс старой сборки перезапускается сам.
- Профиль берётся из сиблинга `../agctl-profile-<id>` (или
  `LOCAL_PROFILE_DIR`): `local_up` сам создаёт ссылку
  `~/.agctl/profiles/<id>` на этот репозиторий — её читают и `agctl dev`,
  и `make img_*`, и `make up PROFILE=<id>`; внутри репозитория agctl
  ссылок и копий профиля нет. Правка профиля применяется после `local_down` и `local_up`.
- Порт профиля выбирается один раз — первый свободный с 8931 — и хранится
  в `config.yaml` дома; 8930 закреплён за нейтральным agctl.
- Секреты у каждого дома свои (сервис `agctl:<id>` хранилища ОС); `LOCAL_SECRETS=file` — держать их в файле дома.
- Если в checkout'е есть незакоммиченные правки, `local_up` предупреждает:
  они попали в бинарь.

### Обновление dsh

Пин dsh — `ARG DSH_VERSION` в `internal/assets/image/Dockerfile`; свежие
версии npm выходят под dist-tag `next` раньше, чем `latest`. Сверка и
подъём пина — `bin/dsh-bump.sh`: без аргументов показывает пин и оба
канала, `--check` (exit 1 при дрейфе, ворота по умолчанию по `next`),
`--update [--channel latest|next]` двигает пин в рамках rc-политики
(alpha/beta/dev не ставятся в любом канале). После `--update` — собрать
образ и прогнать e2e (`make img_build && FAKE_LLM=1 bin/e2e-smoke.sh`).
Воркфлоу `dsh-bump` делает это еженедельно сам: PR с подъёмом пина по
`latest` (полный конвейер: go/SPA, образ, e2e-smoke) и отдельная проверка
`next` — образ собирается на её версии без изменения пина
(`make img_build IMG_BUILD_ARGS="--build-arg DSH_VERSION=<next>"`) и
проходит тесты плагинов и `bin/e2e-first-session.sh`; при провале
заводится issue, пин не двигается.

## Карта системы

```bash
make map
```

Открывает `system/map/index.html` с четырьмя вкладками: «Сервер — один хост»,
«Ноутбук — локальный режим», «Кластер: k8s | ax» и «Бинари и код» (какой код
входит в `agctl`, `agctl-server` и `agctl-guest`). Карты собираются archify
из спецификаций `system/map/*.architecture.json`, их улики ведут в строки
кода; `make map_check` проверяет улики против текущего дерева,
`make map_build` пересобирает HTML. На работающем сервере те же вкладки —
страница `/map` после входа.
