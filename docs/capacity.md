# Ресурсная модель: agctl v3, единый runtime на пользователя

> Это планирование, не SLA и не повторный замер. Базовые цифры ниже — старый снимок
> M4 / 24 ГБ от 2026-10-18/19, снятый до объединения чата и разработки. В частности,
> **125 МБ idle — planning estimate: замеры не повторялись на новой совмещённой
> нагрузке** (включая developer SSH, проекты и их autosave). Пилот должен заменить
> эти оценки данными с чистого тома.

## 1. Что осталось от старых замеров

| Исторический показатель | Значение из старого профиля | Как использовать сейчас |
|---|---:|---|
| Один idle-контейнер DSH Web | ~125 МБ (лимит контейнера тогда/сейчас — не фактическое потребление) | Только planning baseline; не измерен заново с sshd и новым профилем проектов |
| Warm start / cold start | ~2 с / ~1 с | Старые цифры, повторить на целевом стеке |
| `dsh headless` на задачу | ~200 МБ / ~0,5 с | Отдельный старый режим, в расчёт персонального runtime не включён |
| `agctl serve` | ~150–200 МБ | Ориентир одного control-plane процесса, не повторно измерен |
| Персональные данные | ~50–200 МБ на пользователя | Старый chat-only ориентир; размер проектов и `.git`-истории добавляется и не ограничен этой оценкой |

Старые оценки не складывают отдельные «чат-контейнер» и «dev-контейнер»: такое
умножение больше не соответствует v3. Сервер задаёт по умолчанию лимит 2 ГБ и 2 CPU
на контейнер — это верхний лимит, не оценка его обычного потребления
([параметры `serve`](../cmd/agctl/main.go#L117-L129)).

## 2. Текущая модель контейнеров

- У каждого пользователя **один и тот же персональный контейнер** для `/chat/`;
  отдельного контейнера/места для developer нет. `user`, `developer` и `admin`
  не умножают число runtime. Рантайм создаётся лениво, один `StorageID` привязан
  к пользователю ([`ensureChat`](../internal/server/chat.go#L499-L553),
  [Docker adapter и mounts](../internal/runtime/dockerrt/chat.go#L13-L73)).
- TTL простоя по умолчанию — **60 минут для всех ролей**. По истечении TTL agctl
  удаляет compute-контейнер, оставляя персональные данные на томе; следующее
  обращение снова поднимет runtime ([настройка TTL](../cmd/agctl/main.go#L120-L129),
  [reaper](../internal/server/chat.go#L571-L599)).
- Проект — каталог внутри общего user volume: `chats/u<ID>/work/<name>`.
  DSH Web и его дочерние процессы читают/пишут его напрямую через RW bind mount;
  файловые операции не проксируются через agctl. `work` одновременно является
  mount рабочего пространства; новых volume или клонов на роль/проект нет ([пути проекта](../internal/provision/projects.go#L45-L65),
  [mount общего `work`](../internal/runtime/dockerrt/chat.go#L24-L27)).
- В проекте хранится локальный репозиторий. Периодический autosave вызывает
  `go-git` из Go-кода agctl: локальный commit, без remote/push; это работа внутри
  существующего процесса agctl, не отдельный процесс или контейнер
  ([autosave и исключение credential-файлов](../internal/provision/projects.go#L210-L273),
  [планировщик autosave](../internal/server/server.go#L350-L378)). Git не становится
  частью пользовательского UI. Размер рабочей копии и локальной `.git`-истории
  увеличивает общий диск и требует измерения на пилоте.
- Для developer с SSH-ключом в том же контейнере запускается дополнительный
  `sshd`. Его память **не измерена**; процесс ожидаемо небольшой, но точное число
  не предполагается и в расчёты не подставляется. SSH не создаёт второй runtime
  ([ключ передаётся в общий runtime](../internal/server/chat.go#L536-L540),
  [sshd включается опционально](../internal/runtime/dockerrt/chat.go#L50-L72)).

## 3. Формулы RAM

Обозначения: `N` — число пользователей; `R₀ ≈ 125 МБ` — старый planning baseline
на один живой DSH-контейнер; `B` — память `agctl serve` и прочих host-процессов;
`S` — число живых developer-контейнеров с настроенным SSH-ключом; `Rssh` — память
sshd, пока не измеренная. Каждый такой developer уже входит в число контейнеров `C`.

**TTL = 60 минут**

```text
C60(t) = число пользователей с последней активностью в интервале [t − 60 мин, t]
RAM60(t) ≈ B + C60(t) × R₀ + S60(t) × Rssh,   где S60(t) ≤ C60(t) ≤ N
```

Для планирования по доле `p60` пользователей, активных в скользящем часовом окне,
`C60 ≈ N × p60`. Значение `p60` нужно получить из пилота: старые 7% одновременной
активности чата не являются измерением часового окна TTL.

**TTL = ∞** (контейнер не усыпляется по простою)

```text
C∞(t) = число пользователей, уже открывавших runtime и не выселенных вручную
RAM∞(t) ≈ B + C∞(t) × R₀ + S∞(t) × Rssh,   где S∞(t) ≤ C∞(t) ≤ N
```

При доле `pEver` когда-либо активировавших аккаунтов `C∞ = N × pEver`; верхняя
граница — один контейнер на каждый из `N` аккаунтов. В обеих формулах роли не
добавляют второй множитель контейнеров. Если все учётки уже активировали runtime,
старый baseline даёт следующий **контейнерный-only** worst case; к нему отдельно
добавляются `B` и неоценённая память sshd:

| Пользователей `N` | Живых контейнеров при «все активны» | `N × 125 МБ` — исторический baseline |
|---:|---:|---:|
| 100 | 100 | ~12,5 ГБ |
| 500 | 500 | ~62,5 ГБ |
| 1 000 | 1 000 | ~125 ГБ |
| 5 000 | 5 000 | ~625 ГБ |

Это верхняя граница числа одновременно живых контейнеров, а не ожидаемый пик.
При TTL 60 минут фактическое `C60` определяется активностью за последний час;
при TTL=∞ число живых контейнеров со временем может вырасти до числа всех
когда-либо активировавшихся пользователей.

## 4. Диск, autosave и пилот

На пользователя сохраняется общий том с `dsh-home` и `work`; проекты — каталоги
внутри этого `work`, а не отдельные dev-тома. Приближённая модель диска:

```text
Dtotal ≈ Σusers (D_dsh-home + D_work/.sessions + Σprojects(D_worktree + D_.git))
         + DB + logs + images
```

Старые 50–200 МБ/пользователя не учитывают новый профиль и не задают квоту на
проекты. Нужен **пилот с чистого тома**: иначе старые рабочие каталоги/данные
исказят baseline. На пилоте измерить размер пустого и активного user volume,
рост проектных working tree и `.git`-истории, autosave CPU/I/O, а также idle/peak
память одного контейнера с типичной DSH-сессией и developer-sshd. Проверить
отдельно объёмы с SSH-ключом и без него; точную надбавку sshd не предполагать до
замера.

На macOS процессы контейнера исполняются внутри Linux VM Docker Desktop, поэтому
снимать показатели контейнера и VM нужно отдельно и не путать их с памятью
macOS-процесса Docker Desktop.

## 5. Остаточные ограничения оценки

Односерверный Docker sizing на новом объединённом профиле ещё не подтверждён
пилотным прогоном. **Kubernetes sizing и prototype не production-validated**:
есть прототип Pod/Service/PVC, но нет проверки на живом кластере и оснований
считать таблицы кластерным результатом. Scheduler/PVC attach, RuntimeClass
overhead, реальное поведение target CNI и production backup/retention/encryption
не измерены. Текущий prototype NetworkPolicy ограничивает ingress только relay
портом, разрешает источники из namespace и не ограничивает egress
([K8s policy prototype](../internal/runtime/k8srt/provider.go#L251-L279)).
