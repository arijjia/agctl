## Описание (понимание новой архитектуры)

Решение владельца (2026-10-25, ответы на вопросы
`agctl-hq/docs/v3/unified-runtime-model.md`): режимы «Чат» и «Разработка»
объединяются. У каждого пользователя — **один персональный ленивый
контейнер** (dsh web + relay), который засыпает после **1 часа** простоя и
поднимается при обращении. Режимы превращаются в **роли**:

- `user` — чат + папки-проекты; git для обычных пользователей **полностью
  невидим** (пока никак не показываем);
- `developer` — дополнительно: процесс sshd в том же контейнере, шаблоны
  проектов (комплекты), git-контролы. Роль выдаётся **по заявке с апрувом
  администратора** и после подтверждения привязана к учётке;
- `admin` — как сейчас.

Пилот стартует **с чистого тома** — миграция старых `chats/`+`work/` не
делается. Локальный бэкенд (developer локально запускает бэк) — осмысливается
отдельно позже, существующий experimental-код не трогаем.

Почему так: у пользователя с местами сейчас N+1 контейнеров и N+1 разных
dsh-домов — сессии режимов не видят друг друга; различие режимов ролевое, а
не архитектурное. Математика ресурсов: TTL ∞ на 1000 пользователей = 125 ГБ
RAM (кластер), TTL 60 мин = 12–19 ГБ (один сервер). Подробно —
`agctl-hq/docs/v3/unified-runtime-model.md`.

## План (волны)

1. **Волна A (ядро, эта карточка):** роль `developer` (миграция
   role_requests, заявка/апрув API, привязка к учётке); TTL по умолчанию
   60 мин; SSH в едином контейнере (ChatSpec.SSHPubKey → env → публикация
   :2222 на loopback, `SSHPort` в handle, `/api/me/ssh`); создание
   dev-мест только для роли developer/admin; healthcheck образа + reconcile
   unhealthy (ветка agent/ops-hardening).
2. **Волна B (данные/папки):** проекты = каталоги тома пользователя;
   git-autosave по триггеру (для user — невидимый); сессии в каталоге
   проекта; API каталога проектов.
3. **Волна C (UI):** Кабинет: заявка на роль, SSH-ключ, проекты; единый
   сайдбар; демонтаж двух миров «РЕЖИМОВ».
4. **Волна D (чистка):** рабочие места и их provision — legacy; апрув мест →
   заявки ролей; доки/карта — под новую модель.

## Не делать

- Не мигрировать старые данные (`chats/`, `work/`) — пилот с чистого тома.
- Не трогать local backend (осмыслить отдельно позже).
- Не форкать dsh; git UI обычным пользователям не показывать.

## Критерии готовности

- Роль developer выдаётся только через заявку+апрув и привязана к учётке
  (сохраняется между сессиями).
- Один контейнер на пользователя; TTL по умолчанию 60 минут; после сна
  сессии/файлы на месте.
- У developer в контейнере sshd (key-only, loopback), порт виден в API.
- Обычный пользователь не видит git и не может создавать dev-места.
- Все тесты зелёные; e2e-кабинет не регрессирует (админ = developer-путь).
- Доки (README, architecture, roadmap) и карта системы — под новую модель.
